## Пути

`migrations/`, `core/cmd/migrate/`, `core/internal/dbtest/`. Не менять `web/`, `content/`, `docs/`, контракты.

## Что сделать

1. Миграции goose в `migrations/`, диалект Postgres, одна последовательность. Первая миграция `00001_schemas.sql` (диапазон фундамента 00001–00099):
   - схемы `catalog`, `core`, `compute`, `queue`;
   - роли `loader`, `core_app`, `reader` без паролей в репозитории (роль создаётся, пароль не задаётся);
   - `loader` может писать только в `catalog` (USAGE, CREATE на время миграций не давать роли приложения: после миграции у `loader` есть INSERT, SELECT на будущие таблицы схемы через `ALTER DEFAULT PRIVILEGES`);
   - `core_app` пишет только в `core` так же;
   - `reader` только SELECT на все четыре схемы;
   - владелец объектов миграций — пользователь, которым goose подключается, не роль приложения.
2. `core/cmd/migrate` читает `DATABASE_URL` и применяет миграции вверх. Без аргументов — вверх. Неизвестная команда — ненулевой код.
3. `core/internal/dbtest`: если Docker доступен, поднимает контейнер `postgres:16.15` (если образа нет локально — не скачивать другой мажор; можно `docker pull postgres:16.15` один раз), создаёт базу `ai_mentor_test`, отдаёт DSN и закрывает контейнер в `Cleanup`. Если Docker или образ недоступны, тест вызывает `t.Skip` с причиной, а не падает. Тест пакета проверяет, что после миграции четыре схемы есть и у `reader` нет INSERT в `catalog`.
