# Инструкция оркестратору (Cursor): сборка выпуска 1 платформы

Читайте целиком, прежде чем что-либо делать. Это длинная автономная сессия: человек, который вас запустил, может быть недоступен часами. Задавать ему вопросы и ждать ответа нельзя: любую неопределённость вы оформляете файлом-вопросом (раздел 9) и продолжаете с другим пакетом. Когда человек вернётся, он должен найти ветки с работающим кодом, честный отчёт о том, как далеко вы дошли, и список решений, которые нужны от него и от напарника.

Правила проекта лежат в `AGENTS.md` (Cursor читает его сам). При расхождении с этим файлом права `AGENTS.md`. Предыдущий блок работ, Python-часть каталога, описан в `briefs/ORCHESTRATOR.md`; эта инструкция его продолжает.

## 0. Правила режима

- Вы **оркестратор**: пишете брифы, раздаёте работу исполнителям, принимаете результат, ведёте общие файлы и журнал. Продуктовый код и тесты пишут исполнители (раздел 3). Ваши собственные правки допустимы только для общих файлов (раздел 10), брифов, отчётов и мелких проверочных скриптов.
- Состояние хранится в файлах, а не в вашей памяти. После каждого события обновляйте `docs/handoff/orchestrator-progress-release1.md` (раздел 12). Если контекст разросся или чат начался заново, продолжайте с чистого чтения этого файла, `AGENTS.md` и файла прогресса.
- Приоритет: эта инструкция и `briefs/CURSOR-SETUP.md` (раздел 2) на время сессии отменяют общие правила пользователя про «без роя Task», `plan-approver`, `git push`, PR и `pr-reviewer`. Параллельные субагенты в переднем плане разрешены, GitHub запрещён.
- Нельзя угадывать то, чего нет в спецификациях и решениях (правило D228). Нельзя подгонять результат под зелёные тесты. Нельзя придумывать методику (пороги, таймеры, формулы): это вопрос человеку.
- Честность важнее объёма: лучше принять три пакета и честно отчитаться, чем «закрыть» двадцать на словах.

## 1. Цель и граница

**Цель:** построить выпуск 1 платформы по готовым спецификациям, контрактам и таблицам примеров в порядке «ходячего скелета» (D159): контракт каталога → загрузчик → страница варианта → проверка ответов в Go → журнал попыток → экран репетитора с локальным входом; затем вход через Telegram и согласие; затем уроки, ДЗ, план, конспект и PDF.

**Выпуск 1 включает** (по обзорам областей): модули `docs/platform/` auth, privacy, attempts, answer-check, recheck, notifications, web, ops; `docs/personalization/` lessons, homework, conspect, plan (только статичный план); `docs/catalog/` loader.

**Не входит и не делается:** `queue` и `rt-import` (выпуск 2+), диагностика, оптимизатор, модель знаний, агент и сервис `worker` (спецификаций нет или выпуски 2–4), eval каталога, подпись артефакта minisign (точка расширения). Реальный запуск на сервере, создание Telegram-бота, секреты, юридический статус согласия (`status: published`) — дело человека.

**Реалистичный результат.** За одну сессию вы вряд ли пройдёте все пакеты. Поэтому работа идёт по **фазам** (раздел 4): следующая фаза не начинается, пока предыдущая не принята целиком или заблокирована. Обязательный минимум — фаза 0 и фаза 1 (ходячий скелет). Остальное — по мере лимитов.

## 3. Исполнители и лимиты

Исполнитель — отдельный агент (субагент или параллельный агент Cursor) со своим чистым контекстом. Если субагентов нет, играйте роли по очереди в отдельных чатах: новый чат на каждую роль и пакет.

- Одновременно — **не более 15** исполнителей. Общего лимита запусков за сессию нет. Реальная ширина определяется зависимостями пакетов и общими файлами: запускайте вместе всё независимое, но не ждите впустую и не создавайте пакетов ради ширины.
- Роли: **тест-исполнитель** (пишет только тесты), **код-исполнитель** (пишет только реализацию), **ревьюер** (только чтение). Тест-исполнитель не видит реализации; код-исполнитель не вправе менять тесты (D72).
- **Модели:** все роли на Grok 4.7, меняется только effort (таблица в `briefs/CURSOR-SETUP.md`, раздел 5). Ширину держите около 4–6 одновременных исполнителей ради лимита, потолок остаётся 15. Шаблоны ролей (тест-исполнитель, код-исполнитель, ревьюер, член консилиума) — там же, раздел 4; по каждому пакету — таблица «Раздача» ниже. Независимость тестов и кода держится на разных контекстах и замороженных тестах. Перед работой с библиотекой читайте её документацию через Context7.
- Бриф исполнителю самодостаточен: роль, цель, источники (какие файлы читать), пути, интерфейс, запреты, команда приёмки, критерий готовности. Исполнитель не видит вашего разговора.
- Результату не верьте на слово: приёмка вашими руками (раздел 7). Оборвавшийся запуск — не провал: проверьте диск и либо примите по проверкам, либо разделите пакет. Не повторяйте запуск вслепую.

## 5. Как работает проверка: тесты пишутся до кода

Тесты пишутся **первыми** и **другим исполнителем**, чем код (D72). Источник тестов — таблицы примеров (`*.examples.yaml`), которые утверждены людьми и заморожены (D131, D133); их исполнитель **не меняет**. Тест-исполнитель пишет:

- привязки сценариев таблиц к прогонщику F2 (функция `given` для модуля);
- по крайней мере один тест на каждый номер правила спецификации (имя теста содержит номер, например `TestAC_R7_...`);
- тесты границ: чужая запись, чужой ученик, повтор запроса с тем же ключом, права ролей, ключ не утекает до попытки.

Красные тесты допустимы только из-за отсутствия реализации. Для веб-пакетов: тесты компонентов `vitest`; сквозные тесты в браузере — только если браузер уже установлен, скачивать нельзя.

## 6. Изоляция: git worktree и ветки

```bash
git checkout -b feat/release1                       # один раз
echo .worktrees >> .git/info/exclude              # worktree внутри репозитория: Cursor не разрешает правки вне рабочей папки
mkdir -p .worktrees
git worktree add .worktrees/<пакет> -b feat/r1-<пакет> feat/release1
```

- Один пакет — один worktree; исполнитель не выходит за его пределы.
- Python: общее окружение `.venv` в корне (`python3 -m venv .venv && .venv/bin/pip install -r tools/requirements.txt`), абсолютный путь к нему даётся исполнителям.
- PostgreSQL для тестов: один контейнер `postgres` (образ официальный, версия закреплена в F0); `docker` и `psql` на машине есть. С 15 параллельными пакетами у **каждого worktree своя база** (`CREATE DATABASE` из шаблона с уникальным именем по имени пакета) и свой порт сервера в тестах, иначе тесты соседей мешают друг другу. Если контейнер поднять нельзя, пакеты с БД проверяйте на том, что доступно, и в отчёте напишите «не проверено на реальной БД» для каждого такого пакета.
- Приёмка прошла → `git checkout feat/release1 && git merge --no-ff feat/r1-<пакет>`, затем `git worktree remove`. Ветку пакета не удаляйте. Заблокированный пакет не вливается.
- Коммиты: заголовок строго `тип(область): тема` (`feat(core): add attempts journal`), один `-m`, без строк об авторстве ИИ; в `git add` файлы перечисляйте явно (`-A`, `--all`, `.` хук отклоняет).

## 7. Цикл на пакет и приёмка

1. **Бриф.** Напишите `briefs/r1-<пакет>.md` по образцу `briefs/catalog-ci-1.md`: интерфейс, правила с номерами, пути, запреты, команды приёмки. Если бриф нельзя сделать однозначным без решения человека, пакет блокируется (раздел 9).
2. **Тесты.** Тест-исполнитель пишет тесты. Вы проверяете: сборка проходит, на каждый номер правила есть тест, чужое не тронуто, красные только из-за отсутствия реализации. Одна повторная постановка. Затем коммит `test(core): ...` — **точка заморозки**, запомните хеш.
3. **Код.** Код-исполнитель (другой агент или чат) пишет реализацию. Ему запрещено менять тесты и выходить за пути пакета.
4. **Приёмка (вы сами, не по отчёту):**
   - `git diff <хеш-заморозки> -- <тестовые файлы пакета>` пуст;
   - `tools/check-code.sh` проходит целиком: все линтеры и анализаторы из F0 без ошибок (подавлять правило можно только комментарием с причиной), `go test -race`, `vitest`, `tsc`, ESLint и Prettier, `ruff`; генерация типов совпадает с закоммиченной; новые уязвимые зависимости не добавлены;
   - `tools/check.sh` проходит целиком (документация и Python);
   - изменены только пути пакета; нет вызовов внешних сетей, нет лишних зависимостей, нет секретов;
   - выборочно 3–5 ручных проверок вне тестов (свои запросы на плохих и хороших входах, в том числе на чужие права и повтор запроса);
   - для пакетов с запросами: в ответах до попытки нет ключей (WB-R4), все POST требуют CSRF и проверки Origin;
   - запрещённое не затронуто (раздел 11).
5. **Ревью.** Ревьюер (только чтение, другая модель) сравнивает код со спецификацией по номерам правил: расхождения, не пойманные тестами. Подтверждённые находки — код-исполнителю одной постановкой.
6. **Слияние** в `feat/release1`; запись «закончил» в `docs/handoff/entries/` с уникальным именем; обновление файла прогресса.
7. Приёмка не прошла: одна повторная постановка с точным списком замечаний; снова не прошла — пакет **заблокирован**.

В конце каждой фазы — **перекрёстное ревью фазы** двумя ревьюерами с разными срезами (например «права и безопасность», «соответствие спецификациям и контрактам») по всей интеграционной ветке; результаты в отчёт.

## 8. Самовосстановление

- Исполнитель вернул пустое, оборванное или «всё сделано» без файлов: проверьте диск; нет изменений — одна повторная постановка, затем блок.
- Запуск оборвался, но файлы есть: проверьте их приёмкой; не повторяйте вслепую.
- Исполнитель вышел за свои пути: откатите только его файлы в его worktree и поставьте задачу заново с явным запретом.
- Проверки интеграционной ветки сломались после слияния: откатите слияние этого пакета (`git revert -m 1` либо `git reset --hard` на хеш до слияния, **только в локальной интеграционной ветке**), пакет — в заблокированные.
- Инструмент или хук отказал: прочитайте причину; если это правило репозитория, следуйте ему и не обходите.
- Сомневаетесь, что действие обратимо: не делайте его, запишите вопрос.

## 9. Автономность и консилиум

Работайте максимально автономно: до человека должно доходить только то, что нельзя решить без него. Порядок при любом вопросе (ваш, исполнителя или ревьюера):

1. **Ответ в источниках.** Перечитайте спецификацию, таблицы примеров, глоссарий, журнал решений (идите по цепочке колонки «Изменено»), документацию библиотеки через Context7. Большинство вопросов закрывается здесь. Консилиум не собирают по тому, что написано в источниках.
2. **Класс вопроса.**
   - **Инженерный** (выбор между рабочими вариантами, не меняющий смысл правил: структура пакетов, библиотека, форма таблицы там, где спецификация оставляет свободу, способ вывода PDF, обработка ошибок) → консилиум.
   - **Предметный или методический** (баллы, пороги, формулы, правила предмета, тексты согласия, юридическое: всё, что по D228 и D144 утверждает человек), либо **необратимое или внешнее действие** → человеку, файлом-вопросом (пункт 5). Консилиум здесь только готовит рекомендацию и **не решает**.
3. **Консилиум.** Вы пишете нейтральное описание: вопрос, ограничения, источники, известные варианты (без вашего предпочтения). Запускаете **трёх** членов консилиума одним сообщением, в переднем плане, каждому своя установка: «консерватор» (ближе к тексту спецификации, обратимо), «прагматик» (самое простое рабочее), «критик» (что сломается и как проверить). Они отвечают слепо, не видя друг друга (шаблон роли в `briefs/CURSOR-SETUP.md`, раздел 4). Решаете вы: все трое сошлись, принимаете; двое против одного, принимаете мнение двоих и записываете особое мнение; разошлись трое, один целевой повторный круг по спорной точке, затем выбираете вариант, который ближе к тексту спецификации и легче отменить. Один консилиум на вопрос, не больше одного повторного круга.
4. **Результат.** Запись `docs/handoff/entries/<время>-council-<тема>.md` (вопрос, три позиции, ваше решение и почему) и строка в `docs/decisions/log.md` как «default chosen by the council» со следующим номером из вашего диапазона. Решение временное: оно идёт в отчёт для напарника (D144). После этого продолжайте работу.
5. **Файл-вопрос человеку** (только класс «предметный или необратимое»): `docs/handoff/entries/<время>-orchestrator-question-<пакет>.md` со статусом «заблокировано»: что неясно, на какие правила и решения смотрели, варианты, рекомендация (при желании консилиума). Пометьте пакет заблокированным и переходите к независимому. Не угадывайте и не придумывайте методику.

Спецификации и контракты не правьте. Дефект контракта (нет пути или поля) оформляется вопросом, а не дорисовывается. Разумные значения по умолчанию допустимы только там, где они не меняют смысл правила, и записываются как в пункте 4.

## 11. Запреты (жёсткие)

- **Никаких** `git push`, `gh ...`, слияния в `main`, изменения настроек и защиты репозитория на GitHub, удаления чужого. Вся работа остаётся в локальных ветках и worktree. Репозиторий публичный (D142).
- Не читать и не копировать приватные данные: каталог `/home/stranger/projects/tutoring/` и любые сведения об учениках. В коде, тестах и примерах только выдуманные данные.
- Никаких настоящих секретов: токен Telegram-бота, ключи, пароли не создавать и не искать; в коде только имена переменных окружения и тестовые значения. Telegram, LLM и любые внешние сервисы **не вызывать**.
- Не менять: `docs/` (кроме общих файлов раздела 10 и записей журнала), `docs/contracts/`, `legal/`, таблицы примеров `*.examples.yaml`, замороженные тесты.
- Не придумывать коды ошибок, поля, маршруты, id вне спецификаций, контрактов и брифа. Не менять методику (баллы, пороги, формулы).
- Зависимости: **сначала готовые библиотеки** по правилам `briefs/CURSOR-SETUP.md` (раздел 4: поддержка, лицензия MIT/BSD/Apache/ISC, закреплённая версия, проверка API через Context7). Нельзя: GPL и AGPL, чужие установочные скрипты (`npm ci --ignore-scripts`), скачивание и запуск кода вне публичных реестров, вызовы внешних сервисов из кода и тестов (Context7 только для документации). Единственный образ контейнера по умолчанию — официальный `postgres` с закреплённой версией; другие образы только по решению D300+ с причиной (например, для PDF).
- Не ждать человека и не останавливаться «до ответа».
