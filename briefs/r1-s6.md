# Бриф: S6, перепроверка и внутренний API

Для тест-исполнителя, затем для код-исполнителя. Сначала прочитайте `briefs/r1-finish-common.md`. Источники целиком: `docs/platform/recheck.md`, `recheck.examples.yaml`, `docs/catalog/loader.md` (LD-R11, LD-R12, LD-R13), `loader.examples.yaml`, `docs/catalog/plan-import.md` (LP-R6…LP-R16), `plan-import.examples.yaml`, `docs/platform/ops.md` (OP-R17), `docs/platform/auth.md` (AU-R7), `docs/contracts/internal-api.yaml`, `docs/contracts/core-api.yaml` (`getRecheckReport`), решения D170, D173, D197, D275.

## Пути

- `core/internal/recheck/` — логика перепроверки и `Handler()` с `getRecheckReport`.
- `core/internal/internalapi/` — новый Go-пакет: `Handler() http.Handler` с четырьмя операциями внутреннего API. Пакет `core/internal/plan/` не трогать (там работает S4): `importPlan` пишет таблицы плана своим SQL из `internalapi`.
- `content/loader/`, новые тесты `content/tests/test_loader_s6*.py`.
- Новый файл `core/internal/e2e/loader_s6_test.go` (только тест-исполнитель, по образцу тестов этого каталога).
- Миграции `migrations/15001…15999`, один файл `core/cmd/server/mount_s6_test.go`.

## Операции

Внутренние, на `internalapi.Handler()`:

- `announceCatalogVersion` `POST /internal/catalog-versions` (LD-R11, LD-R13, D173)
- `startRecheck` `POST /internal/rechecks` (RC-R1…RC-R5)
- `getRecheckState` `GET /internal/rechecks/{correction_id}` (RC-R6)
- `importPlan` `POST /internal/plan-imports` (LP-R6…LP-R16, D197)

Сервисный токен (`CONTENT_API_TOKEN`, D170) проверяет сервер в `core/cmd/server`, до вашего обработчика. `internalapi.Handler()` токен не проверяет и cookie не читает. Статус отказа по токену в новых тестах не закреплять: замороженный тест S1 ждёт `401`, контракт называет `403`; это расхождение ведёт оркестратор.

Для репетитора, на `recheck.Handler()`: `getRecheckReport` `GET /rechecks/{correction}` (RC-R20).

`getStatus` уже подключён в S1: не трогать.

## Находки ревью, которые надо закрыть

- Загрузчик P1 не вызывает внутренний API: и `announceCatalogVersion`, и передача исправленных ключей на перепроверку только пишут строку `catalog.core_call`. Загрузчик обязан вызывать `core` по-настоящему. Тест — на поднятом сервере (`core/internal/e2e`), не на заглушке.
- D275: в jsonb кладутся не байты хеша.
- Перепроверка не держит один пакет до `done` и не читает `rules_version` (RC-правила, найдите номера в `recheck.md`).
- RC-R13: попытка с ручным вердиктом пропускается. Событие пишет S5; здесь читать его по схеме `events.schema.json`, в тестах класть событие в базу напрямую.

Адрес и токен `core` загрузчик берёт из окружения; имена переменных — из `deploy/secrets.md`, новых не выдумывать. Нет имени — строка `ВОПРОС`.

## Тесты

Один тест на каждый номер RC-R, LD-R и LP-R, который относится к операциям выше, плюс границы: повтор пакета перепроверки с тем же `correction_id`, меньший и больший `correction_id`, повтор `announceCatalogVersion` той же версии, план для несуществующего ученика, отчёт перепроверки чужому репетитору и ученику. Сценарии таблиц примеров для этих операций привязать к прогонщику.
