## Передача на другой аккаунт

1. Перед переключением передайте интегратору последнюю проверенную версию каждой активной работы. Он публикует изменения в рабочих ветках и обновляет [очередь и точки восстановления](../docs/handoff/release1-progress.md#очередь-задач-для-передачи-между-аккаунтами). Сохраните ссылку на ветку или PR реестра, если он ещё вне main.
2. В новом Project прочитайте последнюю опубликованную версию реестра, сверьте каждый статус с GitHub и найдите точный head SHA. Восстановите доску по ID из Git и запишите новые номера карточек для сверки. Закрытые по доказательствам пункты пропустите, работу продолжайте из опубликованной рабочей ветки.
3. Перед повторным назначением проверьте, работает ли прежний исполнитель. У каждой ветки один пишущий владелец. Если старый запуск ещё меняет эту ветку или его состояние неизвестно, сначала передайте владение. Параллельно начните независимый пакет в отдельной ветке.

## Ближайший этап

Подтвердите, что [#28](https://github.com/knowgap-lab/ai-mentor/pull/28) даёт свежему агенту Docker, Postgres, Chrome и возможность повторить smoke. Одновременно назначьте два независимых ревью на технические изменения и критические серверные части, одного интеграционного исполнителя и одного исполнителя сценария API. Уточните доступный лимит перед запуском. Верхний предел в восемь относится ко всем пишущим ролям вместе (D327).

Отдельно можно добавить `.codex/environments/environment.toml` для локального Codex Desktop поверх общих скриптов #28. Эта задача выполняется параллельно и не входит в критерии приёмки серверной основы.

1. Сверить каждый открытый PR с фактической базой и SHA. Проверить самостоятельные изменения и включение голов или патчей в #27. Для замороженных тестов соблюсти D320. После ревью перенести #27 в ветку демо, проверить #6 против свежего main и подтвердить фактическое слияние по правилам репозитория.
2. В отдельной песочнице на кандидате поднять настоящее приложение и чистый PostgreSQL. Загрузить синтетический каталог, создать урок, выдать ДЗ, отправить верный и неверный ответы и проверить баллы, журнал и итог у репетитора. Проверить чужого репетитора и повтор запроса без дубликата. Записать точный шаг первого отказа. Повторить предсказуемый прогон на принятом main SHA.
3. Обновить [реестр прогресса](../docs/handoff/release1-progress.md) и [очередь внешних действий](../docs/handoff/release1-actions.yaml). Сохранить команды, версии, результаты, ссылки на ревью, итоговый SHA и точный следующий шаг. Внешние зависимости останавливают зависимый пакет (D322), пока остальные работы продолжаются.

После принятия серверной основы сразу продолжайте по [этапам полной цели](RELEASE1-GOAL.md#этапы-и-приёмка) и [брифу выпуска](CURSOR-PROJECT-RELEASE1.md). Для каждого этапа фиксируйте исполнителя, принятые критерии и доказательства. Закрывайте цель только после полной приёмки по D321 и D330.
