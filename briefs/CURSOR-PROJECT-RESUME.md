# Продолжение работы над выпуском 1

В новом запуске откройте [AGENTS.md](../AGENTS.md), [цель выпуска](RELEASE1-GOAL.md), [бриф координатора](CURSOR-PROJECT-RELEASE1.md), [сводку](../docs/handoff/LATEST.md) и [реестр задач](../docs/handoff/release1-progress.md). Пока PR #29 открыт, возьмите эти файлы из ветки `docs/r1-repo-handoff`. После её слияния читайте их из `main`. Рабочий код берите из ветки задачи, указанной в реестре.

SHA — идентификатор конкретного коммита Git. Ветка может продвинуться на другой коммит. Чтобы связать тест или ревью с проверенной версией, запишите полный SHA из `git rev-parse HEAD` и ссылку на результат.

2. Выберите для координатора Grok 4.7 Medium без Fast. Отправьте поручение в чат координатора. Если в этом чате доступен `/goal`, используйте ту же формулировку как цель. [Документация Goal в Cursor](https://cursor.com/docs/agent/overview#goals-with-goal)
3. Координатор сверяет выбранный репозиторий, окружение и доступные модели. Первый исполнитель подтверждает доступ к GitHub и полный SHA рабочей ветки. Координатор начинает с двух ролей из [первой волны](CURSOR-PROJECT-RELEASE1.md#12-начало-работы-и-подготовка-запуска). Права на слияние и чистая Ubuntu VM проверяются по мере приближения к соответствующим критериям.

## Сверка очереди ревью

- Просмотрите все карточки `For Review` и `In Progress` по ID. Для задач выпуска найдите строку в Git, ответственного, артефакт или PR, актуальную ветку и SHA. Запишите отсутствующие связки в [реестр](../docs/handoff/release1-progress.md). Карточки вне выпуска отметьте в записи сверки.
- Для каждой задачи `For Review` назначьте недостающее ревью, верните замечания исполнителю или подтвердите принятый результат с коммитом в нужной ветке. Для перенесённых задач и дублей укажите замену и доказательство переноса. Если материалов не хватает, оставьте карточку открытой и запишите препятствие.
- Для карточек `In Progress` выясните, работает ли прежний исполнитель и где опубликован его последний результат. Продолжайте с этой точки после передачи владения. При недоступной доске начните с Git-реестра и доступных PR, запишите предел сверки.
- До интеграции получите требуемые ревью и CI для выбранного SHA. Повторное ревью охватывает изменившийся diff и открытые замечания. Ревьюер первой волны берёт ближайшую блокирующую задачу, а координатор назначает следующие по зависимостям. Два независимых ревью по D320 сохраняются.

## Завершение и пауза

- **Релиз готов** после всех этапов и полного запуска усиленного `python3 tools/release1_done.py` с кодом 0 и доказательствами на одном принятом коммите в `main`.
- **Работа продолжается**, если есть исполнимые задачи. Красный CI или исправимая ошибка требуют диагностики и проверки. Код 2 приёмщика означает внешнее ожидание.
- **Пауза** по просьбе пользователя, при исчерпании включённого лимита или когда все оставшиеся задачи ждут конкретного внешнего действия. Опубликуйте в Git ID задач, ветки и SHA, последний результат, препятствие и условие возобновления. Отметьте зависимость в [реестре действий](../docs/handoff/release1-actions.yaml).

## Передача на другой аккаунт

1. Перед переключением опубликуйте проверенный коммит в рабочей ветке. Передайте интегратору ID задачи, ветку, точный SHA, PR, последнюю команду с результатом и точный следующий шаг. Он обновит реестр и запишет внешние зависимости. Сохраните ссылку на опубликованную версию реестра.
2. На новом аккаунте проверьте доступ к репозиторию и возможности окружения для выбранной задачи. Сверьте доступные ветки и PR с реестром. Клонированию достаточно доступа к Git. Для публикации результатов потребуются права на запись или согласованный путь через форк.
3. Перед повторным назначением выясните, кто держит рабочую ветку. На каждую ветку приходится один пишущий исполнитель. Сверьте колонку ответственного, запись «начал» и актуальную голову ветки. Пока прежний запуск активен или его состояние неизвестно, продолжайте независимую задачу в другой ветке.
4. Если у провайдера есть доска, восстановите карточки по стабильным ID из Git. Номера карточек на новой доске могут отличаться. Сохранённые ветка, SHA и команда позволяют восстановить работу и без доски.

## Рабочий цикл

Перед запуском сверяйте [модели и правила делегирования](CURSOR-PROJECT-RELEASE1.md#модели-и-расход-лимита), [повторное использование результатов](CURSOR-PROJECT-RELEASE1.md#повторное-использование-результатов) и [состав первой волны](CURSOR-PROJECT-RELEASE1.md#12-начало-работы-и-подготовка-запуска). Эти настройки относятся к Cursor. При смене провайдера сохраняйте роли, проверяемый SHA и критерии приёмки.

1. Возьмите готовую к запуску задачу из `Queued`, опубликуйте запись «начал» с ID, исполнителем, веткой и базовым SHA, переведите в `In Progress`. Собирайте в параллельную группу задачи, у которых готовы зависимости и разные области изменений. Общими файлами распоряжается интегратор.
2. После проверки опубликуйте head в PR или рабочей ветке и переведите задачу в `For Review`. Укажите её ID в описании нового PR. Интегратор сверяет каждый вердикт, CI и проверку с точным SHA. При закрытии сохраняет ссылку на результат, команду для повтора и следующий шаг. При замечаниях задача возвращается в `In Progress`.
3. После выполнения критерия и нужного слияния интегратор ставит `Done` и открывает зависимые задачи. Если задача больше не требуется, переведите в `Canceled` с причиной и ссылкой на замену. Внешнее ожидание фиксируется отдельной ссылкой в [реестре действий](../docs/handoff/release1-actions.yaml).
4. Возьмите следующую исполнимую задачу. Если все оставшиеся задачи ждут внешних действий, опубликуйте точку продолжения и запишите, что должно произойти для возобновления.

Независимые изменения с выполненными критериями допускайте к слиянию по мере готовности. Документация и инструменты разработки могут идти отдельными PR. Объединённый продукт проходит собственные проверки перед принятием.

Первый незакрытый критерий и актуальные ветки указаны в [сводке](../docs/handoff/LATEST.md). Общие `tools/dev-install.sh`, `tools/dev-start.sh` и `tools/dev-check.sh` находятся на ветке кандидата. Адаптеры Cursor и Codex Desktop вызывают эти скрипты.

После принятия серверной основы сразу продолжайте по [этапам полной цели](RELEASE1-GOAL.md#этапы-и-приёмка) и [брифу выпуска](CURSOR-PROJECT-RELEASE1.md). Для каждого этапа фиксируйте исполнителя, принятые критерии и доказательства. Закрывайте цель только после полной приёмки по D321 и D330.
