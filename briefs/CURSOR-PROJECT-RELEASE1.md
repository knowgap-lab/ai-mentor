# Задание координатору Cursor Projects: выпуск 1

Редакция по D320–D330. Самостоятельное задание: старые брифы используются для ссылок на спецификации и состав модулей, но их процессные правила не наследуются. Техническая проверка этой редакции и интеграция подготовки предшествуют массовому запуску. Полный выпуск пока не готов.

## 1. Результат

Постоянная цель — `briefs/RELEASE1-GOAL.md`. Проверяемое состояние — `docs/handoff/release1-progress.md`. После каждого возобновления сверяйте цель, граф и доказательства; отмеченный done пакет без проверки не считается принятым.

Подготовьте полный выпуск 1 по спецификациям репозитория и воспроизводимую демонстрацию на чистой Ubuntu VM на компьютере пользователя (D321). В инфраструктуру входят Terraform и Ansible. В демонстрации работают фронтенд, все экраны и карточки, backend, фоновые обработчики, PDF, журналы, мониторинг и вход через Telegram. Используйте только выдуманные данные. Покупка VPS, доменов и приглашение настоящих учеников вне этого запуска.

D322/D325 уточняют Telegram: бот пока не подтверждён. Назначьте отдельного агента для создания и настройки бота и установки runtime-секретов вне git. Основные исполнители готовят код, конфигурацию и автоматические проверки с контролируемым заменителем. Координатор отслеживает результат отдельного агента; это не поручение пользователю создать бота вручную. ACT-TELEGRAM также владеет сетевой схемой: доступный Telegram HTTPS endpoint, привязка адресов к боту, webhook secret, совместимость входа с CSP и проверка подтверждения устройства. Локальный LAN-адрес VM не считается доступным webhook. Используйте существующий разрешённый адрес либо доступный бесплатный туннель, без покупок по D324; публикуется только необходимый HTTP endpoint приложения, не БД, Docker API или административные панели. При отсутствии подходящего адреса/доступа сохраните конкретную внешнюю зависимость, продолжая остальное. Изменение legacy widget на OIDC требует отдельного технического PR по D320. Реальный вход проверяется отдельно после создания бота и безопасной передачи настроек. До этой проверки полный выпуск не завершён; готовую автоматизированную часть можно показывать как промежуточный результат с явным перечнем ожидающих действий.

Различайте три состояния: «продолжаем работу», «вся независимая работа выполнена, ожидается действие человека», «полностью выполнено». Ожидание человека никогда не обозначается словом «готово» применительно ко всему выпуску.

Версия `tools/release1_done.py` из PR #17 — диагностический список, недостаточный для доказательства готовности. До финальной приёмки отдельная сессия пишет и независимые ревьюеры принимают тесты усиленного приёмщика; другая сессия реализует его. Требования этой инструкции и D321–D327 реализуются в защищённом приёмщике отдельным техническим PR с двумя независимыми ревью по D320. Исполнители продукта не ослабляют их. Команда остаётся `python3 tools/release1_done.py`: 0 — полностью выполнено; 1 — продолжать; 2 — внешняя зависимость, только после исчерпания всей независимой работы, не завершённый выпуск. Ошибка самого приёмщика не даёт 0 или 2. `--quick` никогда не подтверждает завершение.

## 2. Роль координатора и исполнителей

Вы — координатор Project: составляете граф работ, ставите задания исполнителям, получаете доказательства, обновляете доску и обеспечиваете продолжение. Не предполагается, что у координатора есть терминал или возможность редактировать файлы. Команды, изменения, проверки, Git и операции с PR выполняют назначенные локальные или облачные исполнители.

Назначьте одного **интеграционного исполнителя**, единственного владельца общих файлов. Выдавайте ему задания последовательно, никогда не запускайте два пишущих задания этой роли одновременно. Его область: `docs/decisions/log.md`, `docs/handoff/LATEST.md`, записи состояния, файл прогресса, очередь действий пользователя, принятые брифы, реестр экранов, общие workflow и `tools/check*.sh`, точка сборки сервера и подключения маршрутов. Изменения этих файлов остальные исполнители передают ему как конкретное предложение с проверкой.

Исполнители продукта владеют только заранее перечисленными путями пакета. Тесты пишет отдельная сессия, код — другая. Ревьюеры и QA независимы от авторов проверяемых изменений. Ревьюер сообщает результат координатору; интеграционный исполнитель сохраняет отчёт с авторством роли и проверенным SHA, не меняя его выводы. Читающие роли не коммитят свои заключения самостоятельно.

Перед первым запуском поручите интеграционному исполнителю прочитать `AGENTS.md`, `docs/handoff/LATEST.md`, две последние записи, `docs/README.md`, `docs/glossary.md`, актуальные цепочки решений; проверить git, незавершённые PR и записать «начал». Существующие незакоммиченные изменения сохраняются и учитываются, а не стираются.

## 3. Источники и полномочия

Источники поведения продукта: спецификации `docs/`, утверждённые таблицы примеров и `docs/contracts/`. Номера, поля, коды ошибок, правила предмета и методика не придумываются. Типы Go, Python и TypeScript генерируются из контрактов (D97). Прежние брифы допустимы как указатели на состав пакетов; их процессные правила, абсолютные локальные пути, запреты сети для установки инструментов и старые лимиты сюда не наследуются.

D320 разрешает технические исправления замороженных тестов и противоречивых инженерных требований: отдельный PR, два независимых ревью и зелёный CI. Автор реализации не меняет замороженные тесты в своём PR. Исправление теста обосновывается правилом и независимым воспроизведением дефекта; ослабление проверки для сокрытия ошибки не разрешено. Предметные правила, ключи, баллы и юридические тексты остаются за человеком.

D328 даёт координатору и локальным/облачным исполнителям выпуска 1 полномочия самостоятельно выбирать обычные инженерные и операционные решения: имена внутренних env-настроек, совместимые версии инструментов/образов, подготовку сервисов, установку зависимостей, работу с ветками, PR и штатным автослиянием. Повторное разрешение на эти действия не запрашивается. Дефект замороженной технической фикстуры/монтажного теста решается отдельным исправлением по D320, а не ожиданием человека или подгонкой реализации.

Интеграционный исполнитель записывает каждое принятое решение следующим свободным номером, с источником и цепочкой отмен. Номер не зашит в инструкции. Новое инженерное решение явно отличать от предложения и от уже утверждённого требования.

Настройки аккаунта, доступы, защита репозитория, включение очереди слияния и разрешения облачной машины меняются только уполномоченным человеком. Отказ хука или защиты исследуйте; исправляйте допустимым способом. Обход, отключение проверки и подмена успешного результата запрещены.

## 4. Параллельность и граф

Запускайте вместе готовые независимые задания с отдельными результатами приёмки. Размер группы выбирайте по зависимостям, доступным слотам Cursor, очереди CI, ресурсам VM и оставшемуся включённому лимиту. Восемь пишущих исполнителей, включая интегратора и вложенных агентов, — верхний предел (D327). Первую волну возобновления начинайте с координатора и двух ролей из раздела 12 (D332).

До запуска у каждого задания должны быть: ID, зависимости, полный список разрешённых путей, базовый SHA, ожидаемые артефакты, команды проверки и критерий приёмки. Даже разные файлы одного пакета могут иметь семантическую зависимость: границы проверяются по смыслу, не только по пути. Переименование или расширение области требует нового назначения до изменения.

Читающих ревьюеров назначайте по рискам конкретного diff. Перед вложенным запуском координатор сверяет ID задачи, пути и уже активных исполнителей. Вложенные работы учитываются в общем лимите и реестре владения.

Для первого разбора нового объёма можно использовать до шести тем Red Team из D327. При продолжении выпуска используйте опубликованные находки и проверяйте изменившийся diff, открытые замечания и новые риски. Для каждой находки сохраните требования, доказательства, последствия, ответственного и проверку исправления. Обязательные независимые ревью по D320 и разделу 6 выполняются на актуальном SHA.

### Модели и расход лимита

- **Координатор** — Grok 4.7 Medium без Fast. Он ведёт очередь, разбирает зависимости и решает порядок интеграции.
- **Обычный исполнитель** — Composer 2.5 Standard. Ему подходят ограниченные изменения, сборка известных веток, документация, воспроизведение тестов и разбор конкретного падения CI.
- **Независимый серверный ревьюер** — Grok 4.7 Medium без Fast. Для задачи с неясным контрактом, правами доступа, замороженным тестом или сложным сбоем интеграции можно повысить effort до High. Сохраните уже собранные факты и продолжайте с того же SHA.
- **Резервная модель** — Grok 4.6 Standard, обычно Medium. У 4.6 и 4.7 одинаковые опубликованные ставки Standard. По опубликованным ставкам сверх включённого лимита на 22 ноября 2026 года входные токены Composer Standard стоили примерно в 4 раза, выходные — в 2,4 раза дешевле, чем у Grok Standard. Расход на принятый результат зависит от длительности и повторных попыток.

Если доступно **Settings → Models → Projects**, укажите модели координатора и воркеров раздельно. Для делегированного задания явно назовите модель и режим. `inherit` использует настройки родителя. Поддерживаемые настройки зависят от тарифа и типа запуска. Проверьте фактическую модель в карточке первого задания и в Usage. Для собственных субагентов примеры модели в конфигурации — `composer-2.5[fast=false]` и `grok-4.7[effort=medium,fast=false]`. Используйте модели из включённого лимита выбранного аккаунта по D324. Ссылки для сверки — [модели и тарифы Cursor](https://cursor.com/docs/models-and-pricing), [настройки Projects](https://cursor.com/docs/release-notes) и [модели субагентов](https://cursor.com/docs/subagents).

### Повторное использование результатов

1. Координатор сверяет реестр, ветки, PR и CI один раз для всей волны. Перед назначением сопоставьте ID задачи, проверяемый SHA и команду. Найдите открытую задачу, работающего исполнителя или опубликованный результат с тем же объёмом. Возобновляйте найденное задание с его ветки.
2. Передайте исполнителю только его ID, разрешённые пути, исходный SHA, относящийся к делу контракт, последний результат и критерий приёмки. Для диагностики приложите первый сбой и ссылку на полный лог. Общую историю чата и повторный обзор репозитория оставляйте координатору.
3. При неизменных SHA, команде и существенных условиях используйте сохранённые результаты. Повторяйте затронутую проверку при изменении дерева, среды или требования, а обязательные сценарии запускайте на объединённом SHA. Облачную сборку освежайте при изменении среды или если этого требует критерий её приёмки. CI отслеживает один назначенный исполнитель. Независимые ревьюеры по D320 формулируют выводы в отдельных сессиях.
4. Сдайте результат с ID, SHA, ссылкой на PR или CI, выполненной командой, фактическим итогом и следующим шагом. По первой волне оцените расход включённого лимита на принятый результат вместе с повторными попытками. Если Usage показывает входные, кешированные и выходные токены, сохраните сводку по моделям и числу попыток. При отсутствии метрик отметьте, что расход не измерен. Следующую задачу выбирайте по качеству результата и фактическому расходу.

Независимые потоки после первичного разбора:

- После B1/B2: S2, S3, S4, S5, S6, S8 параллельно при непересекающихся путях. S7 после интеграции авторов событий S2–S6; не редактировать одновременно их код событий.
- После F1 и нужных S: W4 после S2/S5; W5 после S3/S4/S5; W6 после S4; W7 после S5/S6; W8 после S2/S3. W0 предварительно завершает переезд существующих экранов либо получает точно отделённые файлы, чтобы не пересечься с W4–W8.

- Финальная QA на интегрированном артефакте, затем независимые обзоры безопасности и соответствия спецификациям. Исправления проходят новый цикл проверки затронутого поведения.

## 5. Пакеты и границы

Храните конфигурацию и инструкции по D331. Сохраните принятые ID: A1, B1, B2, F1, M1, S2–S8, W0, W4–W8, C1, L1, E2, E3. Q0 и S1 уже приняты; повторно проверяйте их поведение при затрагивающих изменениях.

- **A1:** единый `mise.toml`, закреплённые инструменты, `.cursor/Dockerfile` и `environment.json`; чистая облачная сборка, Docker и браузер для тестов. Изменения общих workflow передаются интеграционному исполнителю. Окружение должно собираться без пользовательского `.venv` и локальных каталогов. Проверьте инструменты также вне checkout (глобальная конфигурация mise формируется из того же источника), прогрев обязательного образа Postgres во время Cloud Build и точную синхронизацию Python-зависимостей: повторный pip install не должен оставлять удалённые из lock пакеты. Локальный прототип A1 в игнорируемом worktree не является интегрированным или проверенным окружением.
- **B1/B2:** D309–D312, конфигурация и ресурсы в composition root, strict-server из контрактов, единая цепочка middleware, завершение по SIGTERM, sqlc и проверяемые границы модулей. Конфликт D310 «нет реализации — ошибка сборки» с прежним разрешением 501 разрешается отдельным техническим PR по D320. Финальная приёмка никогда не принимает заглушку 501 как готовую операцию.
- **F1:** D315–D318: генерация клиента и схем, тема, общие компоненты, Storybook, MSW, size-limit, Faro, проверки CSP и анимаций. До старта перечислить реальные файлы пилота «Ученик/Задача», включая нужные файлы `web/src/student/`; на время пилота они принадлежат только F1. Переезд замороженных обёрток разрешён в пределах D316, другие исправления — по D320.
- **M1:** D313/D314: Collector, Prometheus, Loki, Tempo, Grafana, Alertmanager; конфигурация и панели кодом, фильтрация чувствительных данных. С S8 заранее разделить точные файлы `deploy/`; общие Compose-файлы пишет интеграционный исполнитель. Полный префикс `deploy/` двум пакетам не назначается.
- **S2:** вход, Telegram, сеансы и приглашения; проверить существующую ветку `feat/r1-s2`, её базу и заморозку, адаптировать и провести новые независимые ревью.
- **S3:** ученики, согласие, архив и обезличивание; **S4:** уроки, расписание, план и подготовка; **S5:** выдача ДЗ, итоги и споры; **S6:** перепроверка, загрузчик и внутренний API; **S7:** конверты событий; **S8:** Gotenberg и PDF. По D329 настройка приложения называется `GOTENBERG_URL`; внутри Compose начальный адрес `http://gotenberg:3000`. Это не секрет и не поле публичного контракта: отсутствие имени в списке секретов не блокирует код. Совместимый образ закрепить версией, сервис подготовить самостоятельно, реальные credentials хранить отдельно. Конкретные операции берутся из контрактов и соответствующих спецификаций, не из сокращённых пересказов.

Перед назначением фиксируются точные пути; это рабочие ID пакетов, а не новые поля/операции контрактов.

## 6. Цикл реализации и PR

1. Тест-исполнитель переводит утверждённые примеры и правила в проверки, включая ошибки, границы прав и повторные запросы. Отдельная проверка подтверждает, что красный результат вызван отсутствием реализации, а не поломанным окружением.
2. Зафиксируйте принятую заморозку: SHA и точный список тестовых файлов. Код-исполнитель получает её и запрет изменения. Для ранее замороженных тестов действует прежняя заморозка с принятыми исключениями.
3. Код-исполнитель реализует пакет в собственной облачной машине/ветке от актуального `main`; локальный исполнитель использует отдельный worktree. Ветка S2 — исключение после проверки её состояния. Каждая ветка имеет одного пишущего владельца в данный момент.
4. Проверяющий исполнитель сам запускает приёмку; сравнивает замороженные файлы, пути и генерацию, проверяет новые зависимости и отсутствие секретов. Слова автора «всё зелёное» недостаточны.
5. Пакет получает независимое ревью; вход, согласие, права и внутренний API — два независимых обзора. Техническое исправление по D320 всегда получает два независимых ревью и зелёный CI отдельного PR.
6. Назначенные исполнители выпуска 1, локальные и облачные, отправляют свои ветки и открывают PR в рамках D328 без повторного разрешения. Коммит/PR: `тип(область): тема`; явные пути в `git add`; без подписи ИИ. Нет прямой записи в `main`, force-push и изменения защиты.
7. Интеграционный исполнитель включает разрешённое автослияние после ревью и успешных обязательных проверок. Он проверяет фактическое попадание PR через настроенную очередь в `main`, а не принимает сообщение о постановке в очередь за слияние.
8. После интеграции обновляет состояние, зависимости и доказательства. Красный CI или подтверждённый дефект порождает исправление; две неудачные попытки не означают, что исправимая работа стала задачей человека. Смените исполнителя, уменьшите пакет либо назначьте исследование причины.

## 7. Приёмка на доказательствах

Усиленный критерий проверяет следующие обязательные требования; старый диагностический gate не заменяет их.

- Чистый checkout интегрированного `main`; фиксированы SHA исходников, образы и версии инструментов. Обязательные CI checks относятся к этому коду; нужные PR влиты. Отчёт хранится отдельно от артефакта, который он описывает, с явной ссылкой на SHA. Новый отчёт не подменяет проверенный артефакт.
- Полностью проходят `tools/check.sh`, `tools/check-code.sh`, генерация с пустым diff, сборки приложения/Storybook и size-limit. Отсутствующая программа, пропуск, timeout и отключённая обязательная проверка означают непрохождение.
- Реестр обязательных операций берётся из утверждённых контрактов и исключений, экранов — из спецификации. По каждому обязательному сценарию есть фактический результат. Комментарий с названием экрана, регистрация маршрута или успешный тест другого экрана не считаются покрытием.
- E2 обращается к собранному приложению с настоящими backend и БД в демонстрационном окружении, не к MSW. Проверяет все экраны/карточки и состояния, роли, отсутствие ключей до разрешённого момента, пользовательские сценарии, мобильную ширину 360 px, доступность, размеры действий и отсутствие горизонтальной прокрутки. Нет ошибок консоли и нарушений CSP; отдельно проверены `prefers-reduced-motion`, динамические элементы, диалоги, toast и графики. Скриншоты помогают ревью, но не заменяют проверки поведения.
- E3 проверяет успешные и отрицательные обращения, схемы, коды, сеансы ученика/репетитора и отдельную авторизацию внутреннего API. Один набор 401/403 не подтверждает реализацию операций. 404 от незарегистрированного маршрута, SPA вместо API и заглушка 501 — провал.
- Нет skipped/disabled обязательных сценариев и открытых обязательных находок. Ревью содержит проверенный SHA, список требований и доказательства закрытия замечаний; после изменения затронутого кода ревью актуализируется. `approve-with-conflicts` не означает полную готовность.
- Приёмщик имеет независимые негативные тесты: активный блокер при зелёных тестах; старое ревью; пропущенный сценарий; ложное покрытие именем в комментарии; заглушка; неверный/дублированный блокер; отсутствие зависимости; ошибка самого приёмщика; несоответствие проверяемого артефакта заявленному SHA.

## 8. Приёмка Ubuntu VM

Виртуализационный backend, поддерживаемая версия Ubuntu и ресурсы VM выбираются и фиксируются отдельно после проверки компьютера пользователя. Не объявляйте наличие KVM, libvirt или другой системы без проверки. Облачная машина Cursor и конечная локальная VM — разные окружения; успешная сборка в облаке не доказывает запуск VM на компьютере пользователя.

Пользователь планирует предоставить VM на своём компьютере; гипервизор и параметры пока не уточнены. Поддержите установку на уже созданную чистую Ubuntu VM по SSH: отсутствие доступа к гипервизору не блокирует подготовку Ansible и приложения. Terraform описывает создание выбранной VM как воспроизводимый путь полного развёртывания; Ansible — конфигурацию ОС, сервисов и приложения. Проверку Terraform нельзя выдавать за выполненную при одной только установке на готовую VM. Зафиксированы версии, образы и зависимости; секреты, state с чувствительными значениями и реальные данные не попадают в публичный git. Разделите два доступа: SSH к гостевой Ubuntu для Ansible и ограниченный доступ локального QA к гипервизору для создания/удаления только отдельной тестовой VM. Первый не подразумевает второй. Отсутствие доступа к гипервизору оставляет Terraform-проверку незавершённой, даже если Ansible успешно настроил гостя. Пользовательские действия с правами администратора выделяются в очередь с точными командами и последствиями.

Независимая QA подтверждает:

1. С нуля создаётся отдельная одноразовая VM и разворачивается проверенный артефакт по документированным командам без ручного редактирования файлов внутри VM.
2. Повторный Terraform plan не требует изменений; повторный Ansible converge не выполняет неожиданных изменений. Допустимые недетерминированные проверки явно объяснены; повторное создание синтетических записей не размножает данные.
3. После перезагрузки VM обязательные сервисы стартуют, readiness успешен, данные сохраняются и основные пользовательские сценарии проходят.
4. Фоновая задача действительно исполняется и фиксирует ожидаемый результат; проверены допустимые повторные попытки и восстановление после прерывания по спецификации.
5. PDF создаётся настоящим Gotenberg, формулы и содержимое доступны, повторная выдача сохранённого снимка имеет ожидаемые байты; недоступность Gotenberg обрабатывается по контракту.
6. Тестовый запрос виден в логах и трассе, метрики доступны Prometheus и панели Grafana отображают данные. Правило оповещения проходит проверку; реальная доставка Telegram отдельно отмечается как проверенная либо ожидающая активации. Токены приглашения/согласия, ответы и персональные сведения отсутствуют в экспортируемой телеметрии.
7. Резервная копия восстанавливается в отдельное чистое окружение; сравниваются заранее заданные синтетические записи и проверяются пользовательские операции. Наличие backup-файла само по себе не доказывает восстановление.
8. Сохранены команды, версии, ресурсы VM, времена, результаты и очищенные от секретов артефакты. Если инфраструктура не позволяет провести конкретную проверку, это незавершённая проверка с планом исполнения, а не успех.

Удалять или пересоздавать можно только явно выделенную тестовую VM и её ресурсы. Существующую пользовательскую VM и данные без отдельного разрешения не затрагивать.

## 9. Очередь зависимостей и действий пользователя

Интеграционный исполнитель ведёт устойчивую очередь в репозитории. Для каждого пункта: уникальный ID, простое описание, владелец, причина необходимости человека, конкретное действие, затронутые пакеты/сценарии, способ проверки, статус и безопасные ссылки без секретов. Файл очереди — `docs/handoff/release1-actions.yaml`; секреты и персональные данные в него не записываются. Это очередь зависимостей, а не автоматическое исключение из приёмки.

Начальные кандидаты: выбрать/разрешить backend VM, доступ к Cloud Agents, необходимые настройки GitHub, доступы, без которых назначенный агент не может создать Telegram-бота или установить секреты вне git. Само создание бота и установка секретов поручены отдельному агенту (D325), а не пользователю. Не запускайте второго агента с той же ответственностью без проверки уже существующего задания. Секрет передаётся непосредственно в защищённый runtime/secret store, не через общий чат, доску или файлы публичного репозитория; при отсутствии безопасного канала фиксируется зависимость и продолжается остальное. Числа анимаций и разрешённые React Bits не считать утверждёнными, если этого нет в решениях. Предметные и юридические вопросы задавать по одному, сначала объяснив последствия.

Недоступный бот останавливает реальную активацию, но не работу над auth, тестами, интерфейсом, окружением, наблюдаемостью и инструкцией. Запись блокера не закрывает связанные тесты. Когда остаются только действия пользователя, сообщите конкретный промежуточный результат и минимальную следующую инструкцию; после действия продолжите с сохранённого состояния.

## 10. Восстановление и финальный отчёт

Промпт не гарантирует непрерывный процесс при лимите сервиса, потере машины или завершении сеанса. После каждой интеграции сохраняйте граф пакетов, base/head SHA, PR, заморозки тестов, результаты, активные назначения и следующий шаг. Перед лимитом — контрольную точку и честный статус. После восстановления сначала сверяйте git/PR/CI и состояние машин; не повторяйте вслепую создание ресурсов или уже выполненную работу.

Если исполнитель оборвался, проверьте его ветку и артефакты; продолжайте с подтверждённого состояния. Если API платформы не позволяет координатору запустить или возобновить задание автоматически, укажите конкретное действие пользователя и продолжайте остальные доступные работы.

Итоговый отчёт содержит проверяемый SHA, перечень требований и сценариев с результатами, ссылки на CI/ревью, протокол чистой VM, восстановления и перезагрузки, состояние настоящего Telegram, остаточные действия человека и команду повторной проверки. Только полное выполнение принятого критерия даёт статус «выпуск 1 полностью выполнен». До этого используйте точный статус и следующий исполнимый шаг.

## 11. Скорость, нагрузка и анимации

D326 задаёт стартовый пилот: 20 активных учеников и 2 репетитора, вымышленные данные, профиль 4 vCPU / 8 GiB RAM со всеми сервисами наблюдаемости. Проверка 50 учеников диагностическая: покажите пределы и узкие места, не превращайте её в бесконечный обязательный проект масштабирования. Поддерживаются только функции выпуска 1; оптимизатор, модель знаний и LLM будущих выпусков сюда не добавляются.

Исполнитель PERF фиксирует версию Ubuntu, виртуализацию, ресурсы, browser/version, viewport, ограничения CPU/сети, seed, cold/warm cache, сценарии и нагрузочный инструмент. Используйте минимум 5 повторов браузерного сценария; нагрузочный прогон — 5 минут разогрева и 20 минут измерений. Стартовая смесь: 60% чтение задания/списка, 30% ответ или сдача, 10% действия репетитора; задержка между действиями 3–10 секунд по воспроизводимому seed. Действия используют действительные сеансы и доступные по контракту состояния; отрицательные сценарии тестируются отдельно и не портят статистику неожиданных ошибок. Нельзя выдавать долю запросов за точное число пользователей или получать зелёный тест одними отказами авторизации.

Для каждого типа действия основной смеси сохраняйте отдельно число попыток/успехов, p50/p95/max, ошибки/timeout, throughput, число активных пользователей и время очереди. По каждому основному типу нужно минимум 100 завершённых измерений; нехватка образцов означает незавершённый замер. Сводный p95 не заменяет показатели чтения задания, отправки ответа, сдачи и просмотра репетитором. Проверка каждого применимого бюджета идёт по типам действий; PDF/worker имеют отдельный профиль и не смешиваются с API. Укажите, что это закрытый пользовательский профиль: при замедлении сервера throughput снижается; фактическую интенсивность нельзя скрывать за числом VU.

Предварительные инженерные бюджеты: p95 чтения API ≤ 500 мс, записи ≤ 1000 мс, без неожиданных 5xx и потери подтверждённых ответов при основной нагрузке. Это стартовые цели для пилота, а не уже доказанные возможности. После пилота исполнитель и два независимых проверяющих фиксируют итоговый профиль и бюджеты отдельным техническим изменением до финальной проверки. Достижимые исходные цели сохраняются; изменение недостижимой цели требует профиля, трасс, причины и нового обоснованного бюджета, а не одного красного прогона. При повторном провале сначала локализуйте причину и измените реализацию; не понижайте критерий в продуктовом PR.

Веб-ориентиры: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1 ([Google Web Vitals](https://web.dev/articles/vitals)). Это ориентиры реального пользовательского опыта; лабораторный прогон не доказывает полевые показатели. Для демонстрации сохраняются лабораторные результаты и interaction traces, а не обещается статистика настоящих учеников. Размер начального JS, ленивая загрузка праздников и PDF/worker latency получают отдельные бюджеты после baseline; Lighthouse 100 не является требованием.

Красивые перелистывания и другие эффекты проверяются на пилоте: запись взаимодействия, отсутствие блокировки ввода/следующего действия, CSP, узкий экран и reduced motion. Для строгого reduced motion одного MotionConfig недостаточно: проверяются и отключаются также fade/opacity transitions. Длительности 300/1500 мс не утверждены. Просмотр пользователем входит в очередь и не блокирует независимый код. Финальный выбор эффектов сохраняет D315–D318 и D323.

## 12. Начало работы и подготовка запуска

1. Координатор на Grok 4.7 Medium без Fast выбирает первый открытый критерий по [сводке](../docs/handoff/LATEST.md) и [реестру](../docs/handoff/release1-progress.md). При следующем возобновлении сверяет #29 и PR #20, #55 и #56, затем путь кандидата #27 через демо-ветку и #6 в `main`. Статусы брать из GitHub при запуске.
2. Начните с одного исполнителя на Composer 2.5 Standard и одного независимого ревьюера на Grok 4.7 Medium без Fast. Исполнитель готовит сборку из согласованных PR, воспроизводит конкретные падения и проводит единый живой сценарий на новом объединённом SHA — репетитор выдаёт ДЗ, ученик отвечает, репетитор видит результат. Ревьюер проверяет серверный diff и закрытие применимых замечаний по точному SHA, с отдельным вторым ревью там, где оно требуется. Следующие независимые пакеты добавляйте по графу после сверки результатов и Usage.
3. Для A1 зафиксируйте успешный активный Cursor Build ID и версии окружения. Проверяйте реальное использование `.cursor/environment.json`: сохранённые окружения могут иметь приоритет. Dockerfile не копирует полный checkout; paths build.dockerfile/context разрешаются относительно `.cursor/`. Install идемпотентен, сервисы стартуют через start/terminals — процессы Build не сохраняются. Источники: [Cursor Setup](https://cursor.com/docs/cloud-agent/setup), [Builds](https://cursor.com/docs/cloud-agent/builds).
4. Если вложенная виртуализация в облаке недоступна, продолжайте тесты Ansible на доступной чистой Ubuntu и все независимые пакеты. Полный Terraform/VM-прогон выполняет назначенный локальный QA после предоставления выделенной VM/доступа; не выдавайте облачный контейнер за VM. Существующие VM и данные не пересоздавать.
5. До полноценного PR-потока нужна интеграция workflow с merge_group в default branch, настроенная очередь и пробный PR с фактическим запуском обязательных проверок merge_group без bypass. Подготовьте точную конфигурацию и проверку для уполномоченного оператора; при отсутствии полномочий изменять защиту не пытайтесь. Пока это внешняя зависимость, продолжайте реализацию и проверки доступных пакетов.
6. Выполните проверку инструментов по `briefs/CURSOR-TOOLS.md`: Context7, браузерные инструменты, git/gh. Локальные MCP и установленный плагин не доказывают их доступность облачным воркерам; неполадки MCP не останавливают независимые работы. Для каждой новой библиотеки проверяйте API закреплённой версии по официальным источникам/Context7, лицензию и совместимость CSP. Не используйте старый выбор Mantine/Radix/PWA из локального шаблона CURSOR-SETUP: действуют D308–D318. Faro требует совместимого приёмника и реального пути данных; при необходимости конкретизируйте Alloy отдельным техническим PR. Не меняйте протокол Telegram молча из-за обновившейся документации.
7. Известный E2E 401 — конкретный открытый дефект, который требуется воспроизвести и исправить. Docker/Chrome/deploy checks, production build, E2E, генерация, contract-live и Storybook/size включаются в CI по мере реализации. Разделите два контура: обязательные PR/merge_group regression jobs проверяют текущий кандидат без требования его предварительного слияния или готовности всего выпуска; post-merge release attestation проверяет чистый main SHA, весь выпуск и внешние активации. Полный gate никогда не является условием слияния PR, которое он сам ожидает, и не блокирует промежуточные пакеты из-за ещё не реализованных других пакетов. В PR обязательны уже реализованные regression suites; новые suites вводятся без пропусков собственных обязательных сценариев. Финальный `release1_done.py` сверяет post-merge attestation и доказательства своего main SHA. Частичные зелёные jobs не объявляют выпуск готовым.
8. D324: дополнительные платные расходы запрещены. Учитывайте лимит всех вложенных агентов. Когда лимит исчерпан, сохраните ветки, задачи и контрольную точку; уведомите пользователя, не покупайте кредиты и не объявляйте работу завершённой.

## 13. Ложные остановки и восстановление работы (D328–D330)

- Разрешение на штатные release-ветки/PR уже дано. Отказ GitHub из-за credentials, защиты или сети описывается точной ошибкой и действием владельца доступа; нельзя вместо него писать «пользователь ещё не разрешил push». Не обходить защиту и не ослаблять CI.
- GitHub не является техническим условием локальной сборки: назначенный интеграционный исполнитель может получить доступные локальные ветки/refs и собрать отдельную интеграционную ветку/worktree, запустить приложение и проверки. Ветки на разных недоступных машинах требуют канала передачи/доступа; местоположения фиксируются, невозможность доступа не выдумывается и не замалчивается. Отсутствие удалённой интеграции всё равно не позволяет объявить финальную main-приёмку пройденной.
- Неполная фикстура, отсутствие владельца отчёта и монтажный тест, принимающий любой 404 за отсутствие маршрута, — кандидаты на технический PR D320. Сначала воспроизведите и сравните с правилом; отдельная тест-сессия исправляет проверку, два независимых ревью подтверждают сохранение intended behavior. Никогда не заменять честный 404 на 204 ради теста и не ослаблять проверку прав.
- Старые SHA/успехи из переписки — указатели для поиска, не доказательства. Найдите машины, ветки, коммиты и freeze; зафиксируйте фактические результаты. Python 3.14 и Docker/Gotenberg — ответственность A1/S8, если установка доступна; их отсутствие само по себе не требует выбора пользователя.
- Перед каждым завершением хода проверьте `next_runnable`: если существует самостоятельное задание, назначьте или продолжите его. После неудачи исследуйте причину, уменьшите пакет либо смените исполнителя; не завершайте весь выпуск сообщением о двух нерешённых технических вопросах.
- Если все оставшиеся работы требуют реального внешнего доступа/критического решения либо исчерпан оплаченный лимит, сохраните цель, точное состояние, доказательства и следующий шаг. Это ожидание, не done. Не выполняйте бессмысленный бесконечный опрос недоступного ресурса.
