# Инструкция оркестратору (Cursor): автономная сессия, Python-блок выпуска 1

Читайте целиком, прежде чем что-либо делать. Человек, который вас запустил, может отсутствовать долго. Задавать ему вопросы и ждать ответа нельзя: любую неопределённость вы оформляете файлом-вопросом (раздел 8) и продолжаете с другим пакетом. Когда человек вернётся, он должен найти готовые ветки, честный отчёт и список того, что нужно решить.

Эта инструкция самодостаточна для запуска в Cursor. Правила проекта лежат в `AGENTS.md` (Cursor читает его сам); при расхождении прав `AGENTS.md`.

## 0. Правила режима

- Вы **оркестратор**: пишете брифы, раздаёте работу, принимаете результат, ведёте общие файлы и журнал. Продуктовый код и тесты пишут исполнители (раздел 3). Ваши собственные правки допустимы только для общих файлов (раздел 9), брифов, отчётов и мелких проверочных скриптов.
- Состояние хранится в файлах, а не в вашей памяти. После каждого принятого или заблокированного пакета обновляйте `docs/handoff/orchestrator-progress.md` (раздел 11). Если ваш контекст разросся или чат начался заново, продолжайте с чистого чтения этого файла, `AGENTS.md` и `orchestrator-progress.md`.
- Работайте, пока очередь пакетов (раздел 4) не пуста и не сработал лимит (раздел 12). Затем напишите итоговый отчёт (раздел 13) и завершите сессию.
- Приоритет: эта инструкция и `briefs/CURSOR-SETUP.md` (раздел 2) на время сессии отменяют общие правила пользователя про «без роя Task», `plan-approver`, `git push`, PR и `pr-reviewer`. Параллельные субагенты в переднем плане разрешены, GitHub запрещён.
- Нельзя угадывать то, чего нет в спецификациях и решениях (правило D228 из `AGENTS.md`). Нельзя подгонять результат под зелёные тесты.

## 1. Что это и какую часть проекта покрывает

Платформа адаптивной подготовки к ЦТ и ЦЭ («ИИ-ментор»). Сейчас документация выпуска 1 закончена, начат код. Порядок сборки выпуска 1 зафиксирован в D159: контракт каталога → загрузчик → страница варианта → проверка ответов в Go → журнал попыток → экран репетитора; затем вход через Telegram и согласие; затем конспект и PDF.

**Эта инструкция покрывает только Python-часть первых шагов D159**, то есть работу с каталогом контента:

1. довести проверку каталога `content/catalog_ci/` (структура уже готова, пакет 1, 42 теста): разбить на модули, добавить проверку истории и проверки ключей и пула вариантов;
2. собрать артефакт каталога `content/catalog_artifact/`;
3. сделать импорт плана `content/plan_import/`;
4. (если останется время и лимит) детерминированную часть скилла-составителя `tools/composer/`.

**Что сюда не входит и чего вы не делаете:** платформа на Go (проверка ответов, попытки, перепроверка, вход, приватность, уведомления, очередь, импорт РТ, эксплуатация), веб-интерфейс, экран репетитора, модули персонализации (диагностика, оптимизатор, модель знаний, агент — их спецификаций ещё нет), юридические тексты. Они ждут решений человека и напарника (ревью путей API D269, значения по умолчанию, выбор генераторов типов) и в эту очередь не входят.

Критерий завершения: каждый пакет раздела 4 либо **принят** (все критерии раздела 6), либо **заблокирован** (причина записана); всё принятое влито в интеграционную ветку; `tools/check.sh` на ней проходит; отчёт написан.

## 3. Исполнители и лимиты

Исполнитель — отдельный агент (субагент или параллельный агент Cursor) со своим чистым контекстом. Если в вашем окружении субагентов нет, играйте роли по очереди в отдельных чатах (новый чат на каждую роль и пакет), а разделение «тесты ≠ код» обеспечивайте проверкой git (раздел 6).

- Одновременно — **не более 15** исполнителей. Общего лимита запусков за сессию нет. Реальная ширина определяется зависимостями пакетов и общими файлами: параллельно запускайте всё независимое и не ждите без нужды, но и не создавайте пакетов ради ширины.
- Роли: **тест-исполнитель** (пишет только тесты), **код-исполнитель** (пишет только реализацию), **ревьюер** (только чтение). Тест-исполнитель не видит реализации; код-исполнитель не вправе менять тесты (правило D72).
- **Модели:** все роли на Grok 4.7, меняется только effort (таблица в `briefs/CURSOR-SETUP.md`, раздел 5). Ширину держите около 4–6 одновременных исполнителей ради лимита, потолок остаётся 15. Шаблоны ролей (тест-исполнитель, код-исполнитель, ревьюер, член консилиума) — там же, раздел 4; по каждому пакету — таблица «Раздача» ниже. Независимость тестов и кода держится на разных контекстах и замороженных тестах. Перед работой с библиотекой читайте её документацию через Context7.
- Каждому исполнителю: самодостаточный бриф с заголовком (роль, команда приёмки), целью, источниками, путями, интерфейсом, запретами и критерием готовности. Исполнитель не видит вашего разговора.
- Результату исполнителя не верьте на слово: приёмку проводите сами (раздел 6). Оборвавшийся запуск — не провал: проверьте, что записано на диске, и либо примите по проверкам, либо разделите пакет. Не повторяйте один и тот же запуск вслепую.

## 5. Изоляция: git worktree и ветки

```bash
git checkout -b feat/python-block              # от текущей ветки; один раз
echo .worktrees >> .git/info/exclude              # worktree внутри репозитория: Cursor не разрешает правки вне рабочей папки
mkdir -p .worktrees
git worktree add .worktrees/<пакет> -b feat/<пакет> feat/python-block
```

- Один пакет — один worktree. Исполнитель получает путь worktree как рабочий каталог и не выходит за него.
- Окружение Python — общее: `python3 -m venv .venv && .venv/bin/pip install -r tools/requirements.txt` в корне основного репозитория (каталог `.venv/` игнорируется git); исполнителям даётся абсолютный путь `.../ai-mentor/.venv/bin/python`. Если установка зависимостей недоступна, остановитесь и запишите это в отчёт; не пытайтесь обойти.
- Приёмка прошла → `git checkout feat/python-block && git merge --no-ff feat/<пакет>`, затем `git worktree remove .worktrees/<пакет>`. Ветку пакета не удаляйте.
- Заблокированный пакет в интеграционную ветку не вливается; его ветку и worktree оставьте как есть.
- Коммиты: заголовок строго `тип(область): тема` (`feat(content): add history checks`), один `-m`, без строк об авторстве ИИ; в `git add` файлы перечисляйте явно (`-A`, `--all`, `.` хук отклоняет).

## 6. Цикл на пакет: сначала тесты, потом код

Тесты пишутся **до** кода и **другим** исполнителем. Порядок для каждого пакета:

1. **Бриф.** Напишите `briefs/<пакет>.md` по образцу `briefs/catalog-ci-1.md`: интерфейс, коды или правила с точными условиями, ограничения, критерии. Если бриф нельзя сделать однозначным без решения человека, пакет заблокирован (раздел 8).
2. **Тесты.** Тест-исполнитель пишет тесты в worktree, опираясь на бриф, спецификацию и таблицы примеров (D133), без реализации. Вы проверяете: тесты собираются (`pytest --collect-only`), на каждый код или правило есть тест, чужое не тронуто, красные только из-за отсутствия реализации. Замечания: одна повторная постановка. Затем коммит `test(content): ...` — это **точка заморозки**, запомните хеш.
3. **Код.** Код-исполнитель (другой агент или другой чат) пишет реализацию под замороженные тесты. Ему запрещено менять тесты и всё вне путей пакета.
4. **Приёмка (вы сами, не по отчёту):**
   - `git diff <хеш-заморозки> -- <тестовые файлы пакета>` пуст;
   - `cd content && ../.venv/bin/python -m pytest -q` проходит целиком, не только новые тесты;
   - `tools/check.sh` проходит целиком;
   - изменены только пути пакета; нет сетевых вызовов, git, subprocess к внешнему, лишних зависимостей;
   - несколько ручных мутаций вне тестов (свои примеры плохих и хороших входов) дают ожидаемые результаты;
   - запрещённое не затронуто (раздел 10).
5. **Слияние** в интеграционную ветку; запись «закончил» в `docs/handoff/entries/` (уникальное имя с временем и названием пакета).
6. Не прошла приёмка: одна повторная постановка с точным списком замечаний. Снова не прошла: пакет **заблокирован**, переходите дальше.

Как всё проверяется в итоге: замороженные тесты (из спецификаций и таблиц примеров), весь набор `pytest` плюс `tools/check.sh` на каждом пакете и на интеграционной ветке, ручные мутации, независимое ревью кода против спецификации.

## 7. Самовосстановление

- Исполнитель вернул пустое, оборванное или «всё сделано» без файлов: проверьте диск; нет изменений — одна повторная постановка, затем блок.
- Запуск оборвался, но файлы есть: проверьте их приёмкой; не повторяйте вслепую.
- Работа исполнителя вышла за его пути: откатите только его файлы в его worktree (`git checkout`/`git clean` внутри этого worktree) и поставьте задачу заново с явным запретом.
- Сломались проверки интеграционной ветки после слияния: откатите слияние этого пакета (`git revert -m 1` или `git reset --hard` на хеш до слияния, **только в локальной интеграционной ветке**), пакет — в заблокированные с причиной.
- Инструмент или хук отказал: прочитайте причину; если это правило репозитория, следуйте ему и не обходите. Блокирующий отказ записывайте в отчёт.
- Сомневаетесь, что действие обратимо: не делайте его, запишите вопрос.

## 8. Автономность и консилиум

Работайте максимально автономно: до человека должно доходить только то, что нельзя решить без него. Порядок при любом вопросе (ваш, исполнителя или ревьюера):

1. **Ответ в источниках.** Перечитайте спецификацию, таблицы примеров, глоссарий, журнал решений (идите по цепочке колонки «Изменено»), документацию библиотеки через Context7. Большинство вопросов закрывается здесь. Консилиум не собирают по тому, что написано в источниках.
2. **Класс вопроса.**
   - **Инженерный** (выбор между рабочими вариантами, не меняющий смысл правил: структура пакетов, библиотека, форма таблицы там, где спецификация оставляет свободу, способ вывода PDF, обработка ошибок) → консилиум.
   - **Предметный или методический** (баллы, пороги, формулы, правила предмета, тексты согласия, юридическое: всё, что по D228 и D144 утверждает человек), либо **необратимое или внешнее действие** → человеку, файлом-вопросом (пункт 5). Консилиум здесь только готовит рекомендацию и **не решает**.
3. **Консилиум.** Вы пишете нейтральное описание: вопрос, ограничения, источники, известные варианты (без вашего предпочтения). Запускаете **трёх** членов консилиума одним сообщением, в переднем плане, каждому своя установка: «консерватор» (ближе к тексту спецификации, обратимо), «прагматик» (самое простое рабочее), «критик» (что сломается и как проверить). Они отвечают слепо, не видя друг друга (шаблон роли в `briefs/CURSOR-SETUP.md`, раздел 4). Решаете вы: все трое сошлись, принимаете; двое против одного, принимаете мнение двоих и записываете особое мнение; разошлись трое, один целевой повторный круг по спорной точке, затем выбираете вариант, который ближе к тексту спецификации и легче отменить. Один консилиум на вопрос, не больше одного повторного круга.
4. **Результат.** Запись `docs/handoff/entries/<время>-council-<тема>.md` (вопрос, три позиции, ваше решение и почему) и строка в `docs/decisions/log.md` как «default chosen by the council» со следующим номером из вашего диапазона. Решение временное: оно идёт в отчёт для напарника (D144). После этого продолжайте работу.
5. **Файл-вопрос человеку** (только класс «предметный или необратимое»): `docs/handoff/entries/<время>-orchestrator-question-<пакет>.md` со статусом «заблокировано»: что неясно, на какие правила и решения смотрели, варианты, рекомендация (при желании консилиума). Пометьте пакет заблокированным и переходите к независимому. Не угадывайте и не придумывайте методику.
