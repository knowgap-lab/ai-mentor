# Инструкция оркестратору: Python-блок выпуска 1

Эту инструкцию читает агент, которому дана длинная автономная сессия. Работайте строго по ней. Состояние хранится в файлах репозитория, а не в вашей памяти: если контекст разрастается, допишите запись в `docs/handoff/entries/` и продолжайте со свежего чтения файлов.

## 1. Цель и критерий завершения

Построить Python-часть выпуска 1 платформы: довести проверку каталога (`content/catalog_ci/`), собрать артефакт каталога (`content/catalog_artifact/`) и импорт плана (`content/plan_import/`) по спецификациям и контрактам репозитория. Сессия завершена, когда каждый из пакетов раздела 4 либо **принят** (все критерии раздела 6), либо **заблокирован** (причина записана, раздел 7), и написан итоговый отчёт (раздел 10). Закончить как «всё принято» не обязательно: честный отчёт о заблокированных пакетах лучше угаданной реализации.

## 2. Что прочитать первым

1. `AGENTS.md` (правила проекта обязательны), `docs/handoff/LATEST.md` и две последние записи в `docs/handoff/entries/`.
2. `briefs/catalog-ci-1.md` — образец брифа; `content/catalog_ci/` и `content/tests/` — образец готового пакета и тестов.
3. `tools/check.sh` и `docs/contracts/README.md` — как проверяется всё.
4. Спецификации пакетов из раздела 4.

## 3. Роли и субагенты

- **Оркестратор (вы).** Не пишет продуктовый код и тесты. Пишет брифы, раздаёт пакеты, принимает результат, правит общие файлы, ведёт журнал. Допустимы только мелкие правки для проверки.
- **Тест-субагент** пишет тесты по брифу и не знает реализации. **Код-субагент** пишет реализацию под замороженные тесты и **не может их менять**. Это всегда два разных запуска (правило D72).
- **Ревьюер** (по желанию, отдельный субагент, только чтение): ищет расхождения кода со спецификацией, которых не ловят тесты.
- Запускайте субагентов доступными вам средствами (инструмент Agent; для исполнителя Codex — `codex:codex-rescue` с `--write --cwd <worktree> --model gpt-5.6-terra --effort xhigh`). Бриф каждому — самодостаточный: цель, источники, пути, интерфейс, чего нельзя, команда приёмки. Окно одного запуска Codex около 570 секунд: пакет должен быть так нарезан, чтобы укладываться; если запуск оборвался по времени, проверьте записанное на диске и при необходимости разделите пакет, не повторяя его вслепую.
- Результату субагента не верьте на слово: запускайте проверки сами (раздел 6).

## 5. Изоляция: git worktree

```bash
git worktree add ../ai-mentor-wt/<пакет> -b feat/<пакет> feat/python-block
```

- Один пакет — один worktree. Субагент получает путь этого worktree как рабочий каталог и **не выходит за него**.
- Своё окружение Python: `python3 -m venv .venv && .venv/bin/pip install -r tools/requirements.txt` в корне основного репозитория (общий для всех worktree по абсолютному пути). Если установка зависимостей недоступна, остановитесь и запишите это в отчёт, не обходите.
- После приёмки: `git checkout feat/python-block && git merge --no-ff feat/<пакет>`, затем `git worktree remove ../ai-mentor-wt/<пакет>`.
- Параллельные пакеты не должны менять одни и те же файлы. Если нужно, ждите.

## 6. Цикл на каждый пакет и приёмка

1. **Бриф.** Напишите `briefs/<пакет>.md` по образцу `briefs/catalog-ci-1.md` (интерфейс, коды ошибок с точными условиями, чего нельзя, критерии). Если бриф невозможно сделать однозначным без решения человека, пакет заблокирован (раздел 7).
2. **Тесты.** Субагент-1 пишет тесты в worktree. Вы проверяете: тесты собираются (`pytest --collect-only`), на каждый код или правило есть тест, чужое не тронуто. Замечания — одна повторная постановка. Затем коммит `test(content): ...` — это точка заморозки; запомните хеш.
3. **Код.** Субагент-2 пишет реализацию. Запрещено менять тесты и всё вне путей пакета.
4. **Приёмка (вы сами, не по отчёту):**
   - `git diff <хеш-заморозки> -- content/tests/<файлы пакета>` пуст (тесты не менялись);
   - `cd content && ../.venv/bin/python -m pytest -q` — все тесты проходят;
   - `tools/check.sh` проходит целиком;
   - изменены только пути пакета; нет сетевых вызовов, git, subprocess к внешнему, лишних зависимостей;
   - выборочные мутации вне тестов дают ожидаемые коды (как делалось для пакета 1).
5. **Слияние** в `feat/python-block` и запись «закончил» в `docs/handoff/entries/`.
6. **Учёт.** Если в окружении работает учёт Fusion, закройте вердикты по задачам субагентов (`accepted` или `rejected` с причиной).

Не прошла приёмка — одна повторная постановка субагенту с точным списком замечаний. Снова не прошла — пакет заблокирован.

## 7. Если вы упёрлись (правило D228)

Нельзя угадывать то, чего нет в спецификациях и решениях. Найдено противоречие, пробел или нужно решение человека: запишите вопрос файлом `docs/handoff/entries/<время>-orchestrator-question-<пакет>.md` со статусом «вопрос» (что неясно, на какие правила и решения смотрели, варианты и ваша рекомендация), пометьте пакет заблокированным и переходите к другому пакету, который не зависит от него. Не правьте спецификации и контракты без записи решения.

## 8. Общие файлы и нумерация

Общие файлы правит **только оркестратор**: `docs/handoff/LATEST.md`, `docs/decisions/log.md`, счётчик в `docs/README.md`, `tools/check.sh`, `tools/requirements.txt`. Субагенты создают только новые файлы в своих путях. Новые номера решений выдаёт оркестратор подряд, начиная с D275, с источником `Interview` только если решение принял человек; ваши собственные значения по умолчанию помечайте «default chosen by the orchestrator».

## 9. Запреты

- **Никаких** `git push`, `gh pr ...`, слияния в `main`, правок настроек или защиты репозитория на GitHub, изменения прав доступа и удаления чужого. Вся работа остаётся в локальных ветках.
- Не читать и не копировать приватные данные: каталог `/home/stranger/projects/tutoring/` и любые файлы с данными учеников. Только синтетические данные (D142).
- Не изменять `docs/` (кроме общих файлов раздела 8), `docs/contracts/`, замороженные тесты, `legal/`.
- Не придумывать коды ошибок, поля, маршруты и id вне спецификаций и брифа.
- Не запускать скачивание внешнего кода (npx, go run, установка генераторов); зависимости только из `tools/requirements.txt`.

## 10. Лимиты и итоговый отчёт

- Не более двух субагентов одновременно; не более двух постановок на пакет; не более трёх заблокированных пакетов подряд (после этого остановитесь и доложите).
- Допускается пакет разделить на два, если он не укладывается в одно окно исполнителя.
- По завершении: запись `docs/handoff/entries/<время>-orchestrator-python-block-done.md` и обновлённый `LATEST.md` со **сводной таблицей**: пакет — состояние (принят, заблокирован) — ветка — чем проверено — вопросы к человеку. Укажите, как человеку проверить результат (`git log feat/python-block`, `tools/check.sh`), и список того, что нужно просмотреть вручную. Сообщите честно, что не получилось.
