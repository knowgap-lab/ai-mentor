# AGENTS.md — правила для любого агента

> Этот файл читает любой ИИ-агент (Claude, Codex, Cursor, Grok и другие) и любой человек, прежде чем что-то менять. Всё, что нужно знать о проекте и текущем состоянии работы, лежит **в этом репозитории**. Ничего не полагайтесь на личную память агента или настройки инструмента.

## 1. Что это за проект

Платформа адаптивной подготовки к ЦТ и ЦЭ (она же курсовой проект «ИИ-ментор»). Сейчас идёт **этап документации**: пишутся спецификации модулей, кода платформы ещё нет. Цель этапа: чтобы агенты потом писали код по спецификациям без догадок.

Команда: два человека. Репетитор и владелец идеи, архитектуры и инфраструктуры — «пользователь»; Go-разработчик — «напарник» (кто что утверждает, см. D144).

## 2. Первые пять минут (обязательно)

1. Прочитайте [docs/handoff/LATEST.md](docs/handoff/LATEST.md): где остановились, что в работе, что дальше.
2. Откройте последние две записи в [docs/handoff/entries/](docs/handoff/entries/). Если последняя запись — «начал», а «закончил» нет, предыдущая сессия оборвалась: сначала разберитесь, что она успела сделать (`git log`, `git status`).
3. Прочитайте [docs/README.md](docs/README.md) и [docs/glossary.md](docs/glossary.md). В проекте у многих слов строго одно значение.
4. Откройте [docs/decisions/log.md](docs/decisions/log.md) и найдите решения по вашей теме. Колонка «Изменено» показывает, чем решение отменено: идите по цепочке до конца.
5. **Запишите в журнал, что беретесь за задачу** (раздел 4), и только потом работайте.

## 3. Правила работы

### Документация и решения
- **Новое решение** записывается строкой в `docs/decisions/log.md` сразу, как только оно принято (следующий номер, источник, дата; если решение отменяет старое, заполните колонку «Изменено» у старого). Номера не переиспользуются, строки не удаляются.
- Спецификации пишутся по [шаблону](docs/templates/module-spec.md). Правило — только «всегда», «никогда» или число, у каждого правила номер, каждое правило должно превращаться в тест.
- Используйте слова только из глоссария. Нужного слова нет — сначала добавьте его туда.
- Чего вы не можете вывести из решений, не угадывайте: запишите вопрос в раздел «Открытые вопросы» спецификации и спросите человека.
- Вопросы человеку задавайте по одному и сначала объясняйте суть простыми словами: люди в команде не обязаны знать терминологию.
- Предметный контент и правила предмета утверждает пользователь, инженерные решения — напарник (D144).
- **Переносите, а не додумывайте.** Когда спецификация берёт что-то из чужих файлов (карточки, планы, исследования), пишите это как цитату с указанием файла. Свою трактовку явно помечайте как трактовку и выносите человеку. Методические элементы (например, «таймер», «блок C», пороги) показывайте человеку отдельно, до того как они станут правилом, даже если они лежат в его же файлах: он мог их не выбирать (D228).

### Процесс разработки (когда начнётся код)
- Цепочка: спецификация → таблицы примеров → тесты → код → ревью (D72). Тесты и код пишут **разные сессии агента**; принятые тесты замораживаются, код-сессия их не меняет.
- Типы для Go, Python и TypeScript генерируются из `docs/contracts/`, руками не дублируются (D97).

### Git
- Рабочая ветка сейчас — `docs/platform-spec`. Новые ветки создавайте только по запросу человека.
- В `git add` перечисляйте файлы явно; `-A`, `--all` и `.` хук репозитория отклоняет.
- Заголовок коммита строго `тип(область): тема` (`docs(catalog): add loader spec draft`). Сообщение — один `-m`, без дополнительных абзацев.
- Не добавляйте в коммиты строки об авторстве ИИ (`Co-Authored-By`, «Generated with…»). Автор коммитов — только человек.
- **Ничего не отправляйте на GitHub без прямой просьбы человека.** Репозиторий публичный, см. раздел 5.

## 4. Журнал передачи состояния (handoff)

Подробный протокол — в [docs/handoff/README.md](docs/handoff/README.md). Коротко:

- Перед работой создайте файл-запись со статусом `начал`: что беретесь сделать и какие файлы затронете.
- После работы создайте вторую запись со статусом `закончил` (или `прервано`): что сделано, что не сделано, что дальше, какие вопросы открыты.
- Обновите `docs/handoff/LATEST.md` — это одна короткая сводка текущего состояния.
- Записи только добавляются, старые не правятся.

Если вы не уверены, что успеете закончить, всё равно пишите запись «начал» — оборванная сессия без следа хуже, чем сессия с незавершённой записью.

## 5. Публичный репозиторий

`knowgap-lab/ai-mentor` на GitHub **публичный** (D142). Поэтому:
- в репозиторий нельзя класть сведения об учениках (имя, город, цель, баллы, класс), реальный каталог с ключами ответов и заметки репетитора. Они живут в отдельном приватном репозитории;
- перед первой отправкой ветку `docs/platform-spec` нужно сжать в один коммит, потому что в ранних коммитах были сведения об ученике;
- примеры в документах пишите на выдуманных данных.

## 6. Чего не делать

- Не менять замороженные тесты и таблицы примеров без отдельного PR и одобрения владельца модуля.
- Не придумывать id, коды ошибок и поля, которых нет в контрактах и спецификациях.
- Не править старые записи журнала и номера решений.
- Не хранить договорённости в личных файлах настроек, заметках агента или чате. Если что-то важно, оно должно быть в репозитории.
