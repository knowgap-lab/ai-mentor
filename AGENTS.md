# AGENTS.md — правила для любого агента

> Этот файл читает любой ИИ-агент (Claude, Codex, Cursor, Grok и другие) и любой человек, прежде чем что-то менять. Всё, что нужно знать о проекте и текущем состоянии работы, лежит **в этом репозитории**. Ничего не полагайтесь на личную память агента или настройки инструмента.

## 1. Что это за проект

Платформа адаптивной подготовки к ЦТ и ЦЭ (она же курсовой проект «ИИ-ментор»). Спецификации написаны, идёт **доделка выпуска 1**: агенты пишут код по спецификациям без догадок. Доделку ведёт координатор Cursor Projects по [briefs/CURSOR-PROJECT-RELEASE1.md](briefs/CURSOR-PROJECT-RELEASE1.md); работа закончена после полного подтверждённого прогона усиленного `python3 tools/release1_done.py` с кодом 0 (D319 → D322 → D327). Текущий приёмщик сначала усиливается по отдельному техническому PR; код 2 означает внешнюю зависимость, а не готовый выпуск.

Команда: два человека. Репетитор и владелец идеи, архитектуры и инфраструктуры — «пользователь»; Go-разработчик — «напарник» (кто что утверждает, см. D144).

## 2. Первые пять минут (обязательно)

1. Откройте [инструкцию возобновления выпуска 1](briefs/CURSOR-PROJECT-RESUME.md), затем [цель](briefs/RELEASE1-GOAL.md) и [сводку](docs/handoff/LATEST.md). Сверьте опубликованные ветки и CI перед выбором задачи.
2. Откройте последние две записи в [docs/handoff/entries/](docs/handoff/entries/). Если последняя запись — «начал», а «закончил» нет, предыдущая сессия оборвалась: сначала разберитесь, что она успела сделать (`git log`, `git status`).
3. Прочитайте [docs/README.md](docs/README.md) и [docs/glossary.md](docs/glossary.md). В проекте у многих слов строго одно значение.
4. Откройте [docs/decisions/log.md](docs/decisions/log.md) и найдите решения по вашей теме. Колонка «Изменено» показывает, чем решение отменено: идите по цепочке до конца.
5. **Запишите в журнал, что беретесь за задачу** (раздел 4), и только потом работайте.

## 3. Правила работы

### Проект как код (D331)

- Храните в Git инфраструктуру, версии инструментов, конфигурацию окружений и CI, команды установки и приёмки, инструкции для агентов, решения и состояние работы. Новый исполнитель должен иметь возможность начать со свежего клона.
- Для ежедневных действий используйте проверяемые скрипты из репозитория. Для неизбежных действий в интерфейсах провайдера опишите шаги, владельца и способ проверки в репозитории. Существенные решения и указания из чата перенесите в соответствующий файл до передачи работы.
- В Git храните имена параметров, схему и порядок подключения секретов. Реальные значения секретов и защищённые данные остаются в назначенном хранилище или приватном репозитории (D142).

### Документация и решения
- **Новое решение** записывается строкой в `docs/decisions/log.md` сразу, как только оно принято (следующий номер, источник, дата; если решение отменяет старое, заполните колонку «Изменено» у старого). Номера не переиспользуются, строки не удаляются.
- Спецификации пишутся по [шаблону](docs/templates/module-spec.md). Правило — только «всегда», «никогда» или число, у каждого правила номер, каждое правило должно превращаться в тест.
- Используйте слова только из глоссария. Нужного слова нет — сначала добавьте его туда.
- Неизвестные предметные, юридические или критические требования не угадывайте: запишите вопрос владельцу и продолжайте независимую работу. Обычные инженерные решения принимайте и документируйте самостоятельно по D328; имя внутренней настройки, версия образа или подготовка сервиса не требуют вопроса человеку.
- Вопросы человеку задавайте по одному и сначала объясняйте суть простыми словами: люди в команде не обязаны знать терминологию.
- Предметный контент и правила предмета утверждает пользователь; инженерные решения — по D144 с исключением D320: технические исправления отдельным PR после двух независимых ревью агентов и зелёного CI.
- **Переносите, а не додумывайте.** Когда спецификация берёт что-то из чужих файлов (карточки, планы, исследования), пишите это как цитату с указанием файла. Свою трактовку явно помечайте как трактовку и выносите человеку. Методические элементы (например, «таймер», «блок C», пороги) показывайте человеку отдельно, до того как они станут правилом, даже если они лежат в его же файлах: он мог их не выбирать (D228).

### Процесс разработки
- Цепочка: спецификация → таблицы примеров → тесты → код → ревью (D72). Тесты и код пишут **разные сессии агента**; принятые тесты замораживаются, код-сессия их не меняет.
- Типы для Go, Python и TypeScript генерируются из `docs/contracts/`, руками не дублируются (D97).

### Параллельная работа (D319, D327)
- Запускайте готовые независимые задачи с разными результатами приёмки вместе. Размер группы и модели выбирайте по [правилам запуска выпуска 1](briefs/CURSOR-PROJECT-RELEASE1.md#4-параллельность-и-граф) и оставшемуся лимиту (D332).
- Пишущих агентов одновременно — не больше 8, включая интеграционного и вложенных исполнителей. Фактические лимиты CI, платформы и оплаченной подписки проверяются отдельно (D324, D327); читающие запускаются по независимым полезным темам, без дублирования ради количества.
- У каждой задачи заранее объявлен список путей, в которые она пишет; две задачи с пересекающимися путями одновременно не идут. Общие файлы (журнал решений, `LATEST.md`, файлы прогресса, `web/screens.json`, `tools/check*.sh`) правит только один назначенный интеграционный исполнитель последовательными заданиями координатора. Координатор Projects планирует и делегирует, сам код не пишет (D327).
- Локально каждая задача работает в своём `git worktree`, в облаке — на своей машине и в своей ветке.

### Автономность
- Цель: `briefs/RELEASE1-GOAL.md`; проверяемый прогресс: `docs/handoff/release1-progress.md` (D330). После возобновления/сжатия контекста сначала сверяйте их с реальными ветками, машинами, файлами и CI.
- Обычные технические и операционные решения принимаются самостоятельно (D328). Список допустимых критических вопросов — в цели; техническая неопределённость сначала исследуется, а не превращается в просьбу выбрать имя переменной.
- Стенд — полный выпуск 1 на локальной Ubuntu VM, инфраструктура Terraform/Ansible (D321). Функции будущих выпусков не добавлять.
- Вопросы, доступы и действия пользователя блокируют только зависимую часть; остальная работа продолжается. Telegram-бот и установка секретов поручаются отдельному агенту (D322, D325).
- Секреты не попадают в git и отчёты. Дополнительные расходы сверх оплаченного лимита запрещены; при исчерпании лимита сохранить состояние (D324).

### Git
- Ветка на задачу от свежего `main`: `тип/<id>-<слаг>`. В `main` напрямую не пишет никто: только PR через очередь слияния после ревью.
- Координатор Cursor Projects и назначенные им исполнители выпуска 1, локальные и облачные, уполномочены коммитить и отправлять свои ветки, открывать PR и включать автослияние через существующие ревью, CI и очередь без повторного разрешения (D328). Перед отправкой исключаются секреты и реальные данные. Прочие сессии не отправляют на GitHub без прямой просьбы. Недоступность GitHub не препятствует локальной интеграции и проверкам; отсутствие доступа фиксируется отдельно.
- В `git add` перечисляйте файлы явно; `-A`, `--all` и `.` хук репозитория отклоняет.
- Заголовок коммита и PR строго `тип(область): тема` (`docs(catalog): add loader spec draft`). Сообщение — один `-m`, без дополнительных абзацев.
- Не добавляйте в коммиты и PR строки об авторстве ИИ (`Co-Authored-By`, «Generated with…», подписи Cursor). Автор коммитов — только человек.
- Force-push, переписывание `main` и изменение настроек репозитория на GitHub запрещены.

## 4. Журнал передачи состояния (handoff)

Подробный протокол — в [docs/handoff/README.md](docs/handoff/README.md). Коротко:

- Перед изменениями опубликуйте в рабочей ветке запись со статусом `начал`: ID задачи, исполнитель, ветка, базовый SHA и файлы. Интегратор обновляет очередь. При отсутствии доступа запишите ближайшую доступную точку передачи и сообщите интегратору.
- После работы создайте вторую запись со статусом `закончил` (или `прервано`): что сделано, что не сделано, что дальше, какие вопросы открыты.
- Интеграционный исполнитель обновляет `docs/handoff/LATEST.md` и реестры выпуска по записям исполнителей.
- Записи только добавляются, старые не правятся.

Если вы не уверены, что успеете закончить, всё равно пишите запись «начал» — оборванная сессия без следа хуже, чем сессия с незавершённой записью.

## 5. Публичный репозиторий

`knowgap-lab/ai-mentor` на GitHub **публичный** (D142). Поэтому:
- в репозиторий нельзя класть сведения об учениках (имя, город, цель, баллы, класс), реальный каталог с ключами ответов и заметки репетитора. Они живут в отдельном приватном репозитории;
- примеры в документах пишите на выдуманных данных.

## 6. Чего не делать

- Не менять замороженные тесты и таблицы примеров без отдельного PR и одобрения владельца модуля. Для технических исправлений действует исключение D320: отдельный PR с двумя независимыми ревью и зелёным CI; код-сессия продукта свои замороженные тесты не меняет.
- Не придумывать id, коды ошибок и поля, которых нет в контрактах и спецификациях.
- Не править старые записи журнала и номера решений.
- Не хранить договорённости в личных файлах настроек, заметках агента или чате. Если что-то важно, оно должно быть в репозитории.
