# Загрузчик каталога

| Поле | Значение |
|---|---|
| Область | catalog |
| Владелец (утверждает) | напарник (D144) |
| Реализуют | content (Python): сборка артефакта в CI и загрузка; core (Go): приём новой версии и перепроверка |
| Выпуск | 1 |
| Решения | D4, D57, D115–D118, D120, D123, D126–D130, D173, D191, D206 |
| Статус | на ревью |

## 1. Назначение

Переносит проверенный каталог из git в базу: собирает артефакт версии в CI, загружает его сначала в staging, потом в prod, и сообщает `core` о новой версии, чтобы тот запустил перепроверку и пересчёт. Загрузчик — **единственный писатель** `catalog.*` (D118).

## 2. Вход и выход

| Вход | Откуда | Контракт |
|---|---|---|
| Исходники каталога на коммите main | приватный репозиторий каталога (D142) | `catalog.schema.json` |
| Подписанный артефакт версии | CI | формат ниже |

| Выход | Куда | Контракт |
|---|---|---|
| Строки `catalog.*` новой версии | PostgreSQL staging, затем prod | `catalog.schema.json` |
| Вызов «новая версия каталога» | `core`, внутренний API | `internal-api.yaml` (D173) |
| Вызов «перепроверка» со списком исправленных ключей | `core`, внутренний API | `internal-api.yaml` (D123) |

### Артефакт версии

Один файл `catalog-<номер>.tar.zst` с подписью рядом:
- `manifest.json`: хеш merge-коммита, будущий `catalog_version`, список всех активных id с хешем содержимого каждой сущности, список `retired` id, список вариантов с исправленным ключом;
- нормализованные данные всех сущностей (JSON по `catalog.schema.json`);
- отрисованные рисунки SVG.

## 3. Правила

### Сборка (CI)

- **LD-R1.** Артефакт собирается только из коммита в main, прошедшего все проверки [schema.md](schema.md), [answer-rules.md](answer-rules.md) и [variants.md](variants.md); из ветки PR артефакт не собирается.
- **LD-R2.** CI подписывает артефакт инструментом minisign; ключ подписи хранится в секретах CI, открытый ключ — на сервере; сервер принимает только артефакт с верной подписью (D191, D215).
- **LD-R3.** Хеш содержимого сущности считается от её нормализованного JSON. Два артефакта с одинаковыми хешами всех сущностей считаются одной версией.

### Версии в базе

- **LD-R4.** Загрузка только добавляет строки и никогда не изменяет и не удаляет существующие (D57).
- **LD-R5.** Номер `catalog_version` монотонно растёт на 1 при каждой загрузке, которая что-то изменила; хеш merge-коммита хранится рядом (D206).
- **LD-R6.** Для каждой сущности хранится ревизия `(id, catalog_version_from, content_hash, данные)`; новая ревизия добавляется, только если `content_hash` изменился. Каталог версии N — это последняя ревизия каждого активного id с `catalog_version_from ≤ N` (D214).
- **LD-R7.** Любую прошлую версию каталога можно прочитать целиком: на неё ссылаются снимки уроков (D120), открытые ДЗ (D117) и попытки.
- **LD-R8.** Повторная загрузка того же артефакта ничего не меняет и не вызывает `core` (идемпотентность).

### Порядок загрузки

- **LD-R9.** Шаги всегда идут в порядке: миграции схемы (отдельный контейнер `migrate`, D127) → содержимое каталога одной транзакцией → вызовы `core` (D57).
- **LD-R10.** Если транзакция содержимого не удалась, в базе не остаётся ни одной строки этой версии, `core` не вызывается, служебный чат получает тревогу (D129).
- **LD-R11.** После коммита содержимого загрузчик вызывает `core` «новая версия» с `catalog_version`; `core` пишет одно глобальное событие и (с выпуска 2) задания пересчёта с ключом «ученик + catalog_version» (D173).
- **LD-R12.** Если в версии есть варианты с исправленным ключом (тот же id, другой ключ, D115), загрузчик вызывает `core` «перепроверка» с `correction_id = catalog_version` и списком id; в выпуске 1 `core` перепроверяет синхронно, перепроверка возобновляется после сбоя с того же места (D123, D126).
- **LD-R13.** Вызовы `core` идемпотентны по `catalog_version`: повтор после сбоя сети не создаёт второго события.

### Окружения

- **LD-R14.** Загрузчик — одноразовый контейнер на сервере, по образцу `migrate`; он скачивает артефакт, проверяет подпись и грузит в одно указанное окружение (D191).
- **LD-R15.** Любая версия сначала загружается в staging. В prod можно загрузить только версию, уже успешно загруженную в staging (D191).
- **LD-R22.** Перенос в prod автоматический: через 10 минут после успешной загрузки в staging, если нет ошибок загрузки и прошли автопроверки staging (D216). Владелец контента может остановить перенос в эти 10 минут командой `hold`; удержанная версия переносится только командой `release`.
- **LD-R16.** Учётные данные базы для загрузчика — отдельная роль, которая пишет только в `catalog.*` (D92, D130).

| Правило | Ситуация | Ожидаемый результат |

| LD-R8 | тот же артефакт версии 8 загружен второй раз | ничего не изменилось, `core` не вызван |
| LD-R7 | урок опубликован на версии 6, сейчас версия 8 | урок показывает блоки версии 6 |
| LD-R10 | транзакция упала на середине | строк версии нет, `core` не вызван, тревога |
| LD-R12 | у V003 исправлен ключ 12 → 14 | вызов перепроверки с `correction_id = 8`, `[ct-math:M14.T07.S1.V003]` |
| LD-R13 | вызов «новая версия 8» повторён после таймаута | одно событие в журнале |
| LD-R15 | попытка загрузить в prod версию, которой нет в staging | отказ `not_in_staging` |
| LD-R22 | версия 8 загружена в staging без ошибок в 12:00 | в 12:10 автоматически загружена в prod |
| LD-R22 | в 12:05 владелец дал `hold` | в prod не идёт до команды `release` |
| LD-R22 | автопроверки staging не прошли | в prod не идёт, тревога |

## 5. Ошибки

| Ситуация | Код | Поведение |
|---|---|---|
| Подпись не совпадает | `signature_invalid` | отказ, тревога, база не тронута |
| Артефакт не прошёл схему | `artifact_invalid` | отказ, тревога |
| Транзакция содержимого упала | `load_failed` | откат, тревога, `core` не вызывается |
| `core` недоступен после коммита | `notify_pending` | повтор с паузой (как в очереди, D148); версия уже в базе, вызов идемпотентен |
| Перенос в prod без staging | `not_in_staging` | отказ |
| Миграция не применена | `schema_behind` | отказ до запуска `migrate` |
