# R3-12 Граница Go и Python

1. **[critical] Worker упал посреди задания: нет аренды, повторов и правила снятия блокировки** (D33, D76, D89, D91, D92). Рекомендация: задание захватывается короткой транзакцией с арендой и счётчиком попыток; блокировка ученика — advisory lock; запись compute.*, проверка watermark и закрытие задания — в одной транзакции; после N неудач — failed и алерт.
2. **[high] Форма задания очереди, слияние и границы watermark** (D81, D87, D89, D92, D97). Рекомендация: тонкое задание {student_id, model|plan, trigger_event_id}; задания одного ученика сливаются; watermark — общая последовательность журнала core, где лежат и факты, и ограничения; новая версия каталога → plan-задание каждому активному ученику; после K перезапусков результат пишется с пометкой «устарел».
3. **[high] Нет контракта для compute.*, которые читает Go** (D24, D91, D92, D97). Рекомендация: представления v_plan_current и v_forecast описаны JSON Schema; план — неизменяемый снимок с plan_version, based_on_event_id, computed_at; у Go только SELECT.
4. **[high] API предложений: гонка версий, идемпотентность, путь до ограничения** (D24, D36, D79, D87, D91, D92, D97). Рекомендация: POST /internal/proposals с idempotency_key и based_on_plan_version; устаревшее предложение → stale_plan и одна перегенерация; одобрение = событие-ограничение в журнале core; аутентификация сервисным токеном.
5. **[medium] Эволюция схем при заданиях в очереди** (D35, D92, D97, S3). Рекомендация: у событий есть schema_version; порядок expand → deploy → contract; представления версионируются; выкладка: миграция → worker → Go; неизвестную версию worker не выбрасывает, а паркует как failed.
